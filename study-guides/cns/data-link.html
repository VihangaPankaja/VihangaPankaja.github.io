Data link framing, errors and flow control

How neighboring devices find frame boundaries, detect corruption, recover missing data, and keep transmissions within receiver capacity.

Big picture

The data-link layer moves a network-layer packet across one adjacent link. It turns an incoming bit stream into recognizable frames, adds checks that help detect corruption, and coordinates recovery and the sender's pace. Those jobs fit together, but they answer different questions: framing asks “where does this unit begin and end?”, error control asks “did it arrive intact, and what now?”, and flow control asks “can the receiver keep up?”

Why links need frames

Synchronization means agreeing on the boundaries of data units. Some links use fixed-size units, such as cells; with variable-length data, the link groups bits into frames. A frame is the Layer 2 unit and carries a packet from the Network layer, with link header and trailer information around it. This is the Layer 2 role in the OSI model (Quiz 1 Q3 and Q9).

The receiver must recognize each boundary even when the payload happens to contain the same pattern used to mark one. The three methods in the lecture solve this in different ways:

Character-oriented framing and byte stuffing

In the lecture's byte-oriented example, FLAG marks the frame boundary and ESC announces that the next byte is payload data, even if that byte equals a reserved value. The sender inserts ESC before a payload FLAG and before a payload ESC. The receiver removes the inserted escape and keeps the following byte. Escaping ESC itself is essential: otherwise a literal escape in the payload would be mistaken for an instruction.

Worked source example: escape reserved bytes and undo the escaping

The four rows below reproduce slide 9. Read the encoded bytes from left to right: after an escape marker, the following reserved byte is literal payload. At reception, consume each escape together with its following byte and output that byte once. Thus A ESC ESC ESC FLAG B decodes as A ESC FLAG B; none of the original bytes is lost.

Bit-oriented framing and bit stuffing

The lecture's flag is 01111110. To prevent that pattern from arising in frame contents, the sender inserts a 0 after any run of five consecutive 1 bits. The receiver removes a 0 that follows five consecutive payload 1 bits. The actual opening and closing flags are not destuffed. Quiz 1 Q4 checks the key idea: a bit-oriented frame is delimited by a flag sequence.

The sender-side rule is from the lecture's example and matches the HDLC-like procedure in RFC 1662 §5.2. The two source inputs differ: the first has no run of six ones; the second does and therefore needs an inserted bit.

Lecture source example 1: no extra bit needed

Input payload: 011100010101111000110. It has no run of five consecutive ones, so the payload is unchanged.

Wire frame: 01111110 | 011100010101111000110 | 01111110.

Receive check: remove the two outer flags; no post-five zero exists to remove, so the recovered payload is the original string.

Lecture source example 2: six adjacent ones

Input payload: 011100010111111000110. The middle contains six consecutive ones. After the first five, insert a zero; the sixth one remains data.

Stuffed payload: 0111000101111101000110 = 0111000101111101000110.

Wire frame: 01111110 | 0111000101111101000110 | 01111110. At reception, after five payload ones, remove the following stuffed zero. The six original ones are restored.

Step through the source bit-stuffing calculation

Insert one zero, then reverse the operation at reception

Given: flag 01111110; payload 011100010111111000110; insert a zero after five consecutive ones and remove that stuffed zero at reception.

1. Keep the flag separate from the payload

Flags are 01111110. Payload starts as 011100010111111000110. Only payload bits are scanned for stuffing.

2. Find the triggering run

The payload contains 0111000101111111000110. Count six adjacent ones. The rule triggers after the first five; the sixth one is data.

3. Insert the transparency bit

Insert 0 immediately after the first five ones: 0111000101 1111101 000110. Removing only visual spaces gives 0111000101111101000110.

4. Add the frame flags

Transmit 01111110 | 0111000101111101000110 | 01111110. The inserted zero prevents a payload flag from being mistaken for a boundary.

5. Receiver reverses the transform

After finding and removing the outer flags, scan the payload. After five ones, discard the next zero: 0111000101111101000110 → 011100010111111000110. This exactly matches the source data.

Stuffing protects boundaries, but it does not detect transmission errors. A lost flag, corrupted data, or an unexpected delimiter can still disrupt synchronization. Checks address corruption; the protocol's boundary rules address framing.

Detecting transmission errors

A noisy link can lose a bit, insert an extra bit, or change a bit from 0 to 1 or from 1 to 0. Errors can be isolated or occur in bursts. The lecture names parity, checksum, and cyclic redundancy check (CRC) as ways to add redundant check information. A sender protects data (sometimes including header fields) with an error-detection code; the receiver recomputes the check on the received data and compares it with the received check field. Slide 15 labels these sent fields D and EDC; the received fields are D′ and EDC′. If the check recomputed from the received D′ does not match EDC′, the receiver reports an error.

Detection is evidence of likely corruption, not a repair operation. No finite check catches every possible error pattern; some errors remain undetected. A detection code therefore needs a separate response such as forward error correction or retransmission. This corrects the loose slide glossary expansion “Error Detection and Correction bits”: here EDC is used as the check/redundancy field, while correction and recovery are separate mechanisms.

Supplemental teaching example: what a parity bit can and cannot detect

The lecture names parity but does not work a numerical parity example. This small example is supplemental. Choose even parity for data 1011001. It has four ones, already even, so append parity bit 0: codeword 10110010. If one data bit flips, the total number of ones becomes odd and the check fails. If two bits flip, parity can remain even; a parity check detects all odd-count flips but can miss an even count. It detects an error; it does not tell the receiver which bit to repair.

Compute and test even parity

Supplemental only: data 1011001, even parity.

1. Count the data ones

Input 1011001 has four ones. The target even count is 4, 6, …

2. Choose the parity bit

Four is already even, so append 0. Codeword: 10110010.

3. Flip one bit

Flip the first data bit: 00110010. It has three ones, so the even-parity test fails and detects corruption.

4. Flip two bits

Starting from the original codeword, flip the first and second data bits: 01110010. It still has four ones, so even parity misses this two-bit error. This is why a check is not a correction guarantee.

The lecture's CRC calculation

The deck calls this a “polynomial code checksum.” It is a CRC-style modulo-2 division: XOR replaces ordinary subtraction, and the generator's degree determines how many zero bits are appended before division. A degree-4 generator therefore adds four zeros. The resulting four-bit remainder replaces those appended zeros. It is a check value, not a set of bits that repairs the message.

This worked calculation preserves slide 16's values. In each division step, align the four-degree generator 10011 with the leftmost 1 of the current five-bit window and XOR. If the window begins with zero, do not XOR; bring down the next dividend bit. The viewer keeps each intermediate window visible instead of skipping to the final remainder.

Worked source example: CRC-style XOR division, every intermediate decision

Generate and verify the lecture codeword

Given: data 1101011011; generator 10011; degree 4; arithmetic is modulo 2, so subtraction is XOR.

1. Append four zeroes

Data 1101011011; generator 10011 has degree 4. Append four zero bits: dividend 11010110110000.

2. Divide the first five-bit window

Window 11010 begins with 1, so XOR the generator: 11010 ⊕ 10011 = 01001. Discard the leading zero and bring down the next dividend bit; the next window is 10011.

3. Divide the next window

10011 ⊕ 10011 = 00000. After discarding the leading zero and bringing down the next bit, the window is 00001.

4. Leading zero: advance without XOR

The window is 00001, so do not XOR the generator. Discard the leading zero and bring down the next bit: 00010.

5. Leading zero: advance again

00010 also starts with 0. Keep the data unchanged, advance, and bring down the next bit: 00101.

6. Advance across the next leading zero

00101 starts with 0, so no XOR is applied. Bring down the next dividend bit: 01011.

7. Advance across another leading zero

01011 starts with 0. Do not XOR; advance and bring down the next bit to obtain 10110.

8. Divide the next leading-one window

10110 ⊕ 10011 = 00101. Discard the leading zero and bring down the next dividend bit: 01010.

9. Advance to the final XOR

01010 starts with 0, so advance without XOR. Bringing down the next bit gives 10100.

10. Divide the final leading-one window

10100 ⊕ 10011 = 00111. After discarding the leading zero and bringing down the final dividend bit, the remainder window is 01110.

11. Read the remainder and verify the codeword

01110 begins with 0, so there is no final XOR. Drop that leading 0: the degree-4 remainder is 1110. Replace the appended zeros to form 1101011011 | 1110 = 11010110111110. Dividing that complete codeword by 10011 gives remainder 0000, an independent check. A nonzero remainder detects corruption (subject to the code’s residual-error limitation).

Error recovery: FEC and ARQ

After a check identifies or suspects corruption, the receiver and sender need a recovery strategy. Forward error correction (FEC) adds enough structured redundancy for the receiver to recover some damaged data without requesting a retransmission. The lecture associates it with simplex transmission, CD-ROMs, high-latency links, voice, and video, where waiting for a return exchange may be undesirable. FEC does not promise zero residual errors.

Automatic Repeat reQuest (ARQ) uses feedback and retransmission. The receiver acknowledges acceptable data; the sender retries after a negative response or when an expected acknowledgement does not arrive by its timeout. ARQ can recover delivery, but the feedback and waiting cost time. Stop-and-wait is simple and may use the link poorly; continuous ARQ keeps multiple frames outstanding with a sliding window.

Stop-and-wait: only one frame is outstanding

The sender transmits one frame, then waits for its acknowledgement before sending the next. The lecture's slide 21 shows successful delivery followed by a lost data frame: silence is resolved by timeout and retransmission. Keep failure cases distinct because they leave different knowledge at the receiver and sender.

Source trace: data frame lost, then timeout and retransmission

Stop-and-wait when data is lost (lecture slide 21)

State: one unacknowledged frame; its timer is running. This is the failure case drawn on slide 21.

1. Successful exchange establishes the cycle

Sender transmits a data frame. Receiver gets it and returns an ACK. The sender can then proceed to its next frame.

2. The next data frame is lost

Sender transmits data, but the receiver gets nothing. Therefore it sends no ACK. The sender cannot infer from silence alone exactly what happened.

3. Sender timeout expires

No ACK has arrived before the timeout. The sender treats the delivery as unresolved and retries the outstanding frame.

4. Retransmission completes the exchange

Receiver gets the retry and returns an ACK. The sender can now advance. Timeout is necessary: waiting forever would deadlock this stop-and-wait exchange.

Supplemental teaching trace: data arrives corrupted

Stop-and-wait when a check fails

Supplemental case: the data frame arrives but fails its error check. The original slide only draws a lost-data timeout.

1. Sender transmits one frame

The frame carries its check information. The sender retains a copy until the exchange is acknowledged.

2. Receiver detects corruption

The received check does not match the data. The receiver does not deliver the damaged payload as good data. It may send a negative acknowledgement where supported; otherwise silence lets the sender timeout.

3. Sender retries the outstanding frame

A NAK or timeout causes retransmission under the protocol’s recovery rule. The exact NAK and timer policy is protocol-specific; the lecture’s stop-and-wait figure does not draw this damaged-frame case.

4. Receiver checks the retry

If the retry passes the check, deliver it and ACK it. The independent check is the receiver's validity test; the retry is the recovery action.

Supplemental teaching trace: ACK lost after successful delivery

Stop-and-wait when the receiver delivered data but the ACK vanished

Teaching example: the protocol uses sequence identifiers to recognize duplicates after an ACK is lost.

1. Receiver gets a valid frame

It checks and delivers the frame, then sends an ACK. The sender still has no proof of delivery until that ACK arrives.

2. ACK is lost

The sender hears nothing and cannot distinguish a lost ACK from lost data using silence alone. It retains the outstanding frame.

3. Sender timeout causes a duplicate transmission

The sender retransmits. This is the same data frame again, not new application data.

4. Receiver uses sequence identity

A stop-and-wait protocol needs a sequence identifier (often alternating between two values) to recognize the retry as a duplicate. It does not deliver the payload twice; it sends the ACK again.

5. Sender receives the repeated ACK

The sender releases the outstanding frame and advances. The receiver's duplicate check prevents duplicate delivery while allowing recovery from the lost ACK.

Supplemental teaching trace: ACK arrives damaged

Stop-and-wait when the ACK cannot be trusted

Supplemental case: a damaged ACK has the same uncertainty at the sender as an absent ACK; it is not the source figure’s lost-data case.

1. Data is accepted

Receiver validates and delivers the frame, then sends an ACK.

2. ACK is corrupted in transit

Sender cannot safely treat an invalid ACK as proof that the frame was accepted. It keeps the outstanding copy.

3. Timeout resolves uncertainty

If no valid ACK arrives before timeout, sender retransmits. The receiver recognizes a duplicate by sequence identity and ACKs again without redelivering it.

Continuous ARQ: sequence state and windows

With continuous ARQ, the sender can send several frames before pausing for acknowledgements. Both ends track sequence state. The lecture writes V(S) for the next frame sequence number to send and V(R) for the next number expected at the receiver. A frame carries its sequence number; a valid in-order frame advances V(R), and the ACK reports that receive state so the sender can release acknowledged frames from its window. A damaged frame can trigger a NAK. Actual timer and recovery policies vary by protocol; the source's “wait till an ACK comes” wording is incomplete, so use its stop-and-wait timeout/retry idea rather than teaching indefinite waiting.

Why the maximum window depends on the ARQ variant

Three sequence bits encode eight values, 000 through 111, cycling modulo 8. For the course quiz's Go-Back-N assumption, a sender window can contain at most seven frames: 23−1=7. This leaves one sequence value to distinguish a new frame from an old outstanding one after wraparound. Quiz 1 Q1 expects 7, but its generic “continuous ARQ” wording leaves the variant unstated.

Selective Repeat can buffer good later frames while a missing frame is recovered. Its sender and receiver windows must avoid confusing old and new sequence numbers after wraparound, so the quiz's Go-Back-N limit must not be applied to every sliding-window protocol. The two recovery procedures below show the distinction taught in the lecture.

Worked example: sequence-space bounds for three-bit numbers

Compare Go-Back-N and Selective Repeat

Given: sequence field width k=3; sequence-space size N=2k; wraparound is modulo N.

1. Count sequence values

Three bits give 23=8 sequence values: 0…7 (or 000…111). After 7, numbering wraps to 0.

2. Apply the Go-Back-N bound

With receiver window 1, the sender window is at most one less than the sequence space: 8−1=7. This is the course quiz answer.

3. Identify the variant

The seven-frame bound assumes Go-Back-N with receiver window 1. A buffering Selective Repeat receiver follows a different window rule; do not generalize the quiz answer to that case.

4. Check the quiz answer

There are eight sequence values. A Go-Back-N sender may have at most seven outstanding frames, leaving one value outside that window. The expected answer is 7.

Two receiver strategies after an error

The source slide 24 contrasts receiver window size 1 with a larger receive window. In the first case, the receiver accepts only the next expected frame. When frame 2 is damaged, later frames are discarded; the sender goes back and retransmits from 2, then continues. This is Go-Back-N / Reject (REJ).

With buffering, the receiver can retain good later frames while frame 2 is missing, then use them after frame 2 is recovered. This is the lecture's Selective Reject picture, corresponding to Selective Repeat / SREJ terminology. The approaches differ in what happens to later good frames, not merely in their names. The mapping of Go-Back-N to REJ and Selective Repeat to SREJ is also used in RFC 3366 and ITU-T V.76 §§6.4.7–6.4.8.

The recovery figures use the slide’s illustrative frame labels, including labels beyond 7. They are logical positions in those examples, not the literal values of a three-bit sequence field. A real three-bit field wraps from 7 to 0.

Source case A: receiver window 1 discards frames after the error

Go-Back-N sequence from slide 24(a)

Source state: receiver window size 1; sequence labels in the slide begin 0, 1, 2, 3…; frame 2 is the error; later good frames are not buffered.

1. Frames 0 and 1 arrive in order

Receiver accepts 0 and 1; the ACK state advances. Sender may keep sending while its window allows.

2. Frame 2 is in error

Receiver cannot advance its expected state beyond 2. Its receive window is size 1, so frame 3 and subsequent out-of-order frames are discarded rather than stored.

3. Later frames are discarded while the gap remains

Slide 24(a) marks the later received attempts as discarded by the data-link layer. The receiver still expects frame 2.

4. Sender retries from frame 2

After the applicable NAK/timeout recovery, sender retransmits frame 2 and the later outstanding frames (the slide shows 2, 3, 4, …). This is why it is called Go-Back-N / Reject.

5. Receiver resumes in order

Once 2 is accepted, the retransmitted later frames can be accepted in sequence. Check: no later payload was delivered before the missing frame.

Source case B: larger receiver window buffers later good frames

Selective recovery sequence from slide 24(b)

Source state: larger receive window; frame 2 is in error; source labels 3, 4, 5 as buffered; NAK/negative feedback identifies frame 2.

1. Frames 0 and 1 are accepted

The receiver advances its expected sequence state through 0 and 1.

2. Frame 2 is damaged; receiver reports the gap

The receiver detects the error at 2 and reports that frame as missing/errored (the source shows a NAK for 2).

3. Good later frames arrive and are retained

Frames 3, 4, and 5 arrive while 2 is missing. Unlike the window-1 case, the larger receiver window buffers these frames rather than discarding them.

4. Sender selectively retries 2

The sender retransmits the missing frame 2. The source figure shows 2 after the later frames have already reached the receiver.

5. Fill the gap, then release buffered frames in order

After 2 passes its check, the receiver can place it before the buffered 3, 4, and 5 and deliver the ordered run. Independent check: the receiver's sequence order is 0, 1, 2, 3, 4, 5 even though arrival order was 0, 1, 3, 4, 5, 2.

Flow control: keep the sender within receiver capacity

Flow control regulates how quickly data is offered so a receiver can keep up. It is not the same as error control: a receiver can be overloaded by correct frames, and a damaged frame can require recovery even when capacity is available.

A brief link to data compression

The lecture also lists data compression among Data Link functions (slide 3) and gives a one-slide illustration (slide 26). Its point is that symbol probabilities can be unequal (P(e)≫P(x)) and that likely next symbols can depend on earlier ones, as in the unfinished “Electroni?” prompt. A compressor can use that statistical redundancy to represent common patterns more compactly. This is a short context link; compression algorithms are not developed in this lecture. Shannon's foundational treatment formalizes source statistics and conditional entropy (Shannon, “A Mathematical Theory of Communication,” 1948).

Slide 27 then connects encryption to security: it lists privacy/confidentiality and authenticity, an algorithm and key, and single-key versus public-key encryption. Detailed cryptography belongs on the Security page. Slides 28–46 develop medium-access methods for shared media; those methods belong on the LAN page, not in this framing and recovery note.

Quick revision and practice

Keep the distinctions straight: framing marks boundaries; a check detects some corruption; FEC adds local recovery redundancy; ARQ retries based on feedback/timeout; flow control protects receiver capacity. In the lecture and Quiz 1, routing between networks belongs to the Network layer (Q5), while synchronization, error control, and flow control are listed as Data Link functions.

Layer 2. It moves packets across an adjacent link inside frames.

After the fifth consecutive one, the sender inserts a zero. The receiver removes that zero after it sees the five ones, restoring all six payload ones.
