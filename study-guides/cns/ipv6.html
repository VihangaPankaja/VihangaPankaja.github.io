IPv6 addressing and transition

IPv6 gives interfaces a 128-bit address and carries packets through a fixed base header that can point to optional extension headers. This page works from address notation and scope to packet handling, coexistence, DNS, and the two-subnet configuration lab.

Big picture

IPv6 was designed to expand the address space and simplify forwarding while leaving room for optional network-layer features. The lecture connects that redesign to a practical problem: IPv4 and IPv6 infrastructure have to coexist while hosts, routers, applications, and DNS records are updated. The address tells us which interface is involved; the header tells routers how to carry the packet and where the next header begins.

The lecture's motivation includes address demand, routing hierarchy, and the effects that private addressing and NAT had on end-to-end visibility. Those are design-era arguments, not a current measurement of IPv4 use or a claim that IPv6 alone supplies security. The detailed proposal history and old allocation tables add little to address use, so they are left out.

Read and shorten an address

An IPv6 address contains 128 bits, written as eight 16-bit hexadecimal groups (hextets). A prefix length counts bits from the left. Many networks use a /64, so four hextets identify the prefix and four identify the interface portion; the exact split depends on the prefix length, not on punctuation.

To write an address compactly, first remove leading zeroes inside each hextet (an all-zero hextet remains 0). Then replace one contiguous run of zero hextets with ::. Expand :: back to enough zero groups to make eight hextets. A canonical rendering chooses the longest zero run; ties go to the first run, and a single zero hextet is not compressed. These canonical tie rules are from RFC 5952.

Worked lecture example: shorten an address in two passes

Shorten the lecture's address without losing any groups

Given: the lecturer's address and the rules above. This is a source example.

Start with eight groups

3ffe:3700:0200:00ff:0000:0000:0000:0001

Count eight hextets before changing notation.

Drop leading zeroes inside groups

3ffe:3700:200:ff:0:0:0:1

0200 becomes 200, 00ff becomes ff, and each all-zero group stays as 0.

Compress the longest zero run

3ffe:3700:200:ff::1

The three adjacent zero groups become ::. Expanding it restores three groups and the original eight-group address.

Teaching example: choose the first of two equally long zero runs
Expand `2001:0:0:1:0:0:2:3` to verify that it contains eight hextets. Both zero runs have length two. Canonical notation compresses only the first longest run, giving `2001::1:0:0:2:3`; the later pair remains explicit. If both runs were compressed, the number of omitted groups would be ambiguous.

Address delivery and scope

Address type answers “who should receive this packet?” Scope answers “how far can it travel?” IPv6 uses unicast, anycast, and multicast; it has no broadcast address. An interface can hold several IPv6 addresses at once, including link-local and global unicast addresses.

Type or form Delivery and useful distinction
Unicast One addressed interface receives the packet.
Anycast Several interfaces share an anycast address; routing delivers to one, usually the nearest according to routing policy. Anycast addresses come from unicast address space.
Multicast All listening members of the destination group receive the packet. One interface may join many groups.
Unspecified :: No address is being asserted; used as a source during some initialization steps, never as an ordinary destination.
Loopback ::1 Refers to this host's own IPv6 stack, like IPv4 127.0.0.1.
Link-local FE80::/10 Used on the directly connected link. Routers do not forward packets with a link-local source or destination. The same link-local value can exist on different links.

Multicast addresses begin with FF; the scope field limits reach, such as node-local (1), link-local (2), or global (E). The lecture also lists site-local scope and a historical flag interpretation; those details are not current deployment guidance. Its FEC0::/10 site-local unicast form is deprecated, as is the old IPv4-compatible tunneling form. See RFC 3879 and RFC 4291. IPv4-mapped forms such as ::ffff:192.0.2.7 are a separate representation used in some APIs; do not confuse them with the deprecated compatible-tunnel form ::192.0.2.7.

An interface may also join all-nodes FF02::1, all-routers FF02::2, and a solicited-node multicast group for address discovery. The solicited-node group is derived from the low 24 bits of a unicast address, so two different unicast addresses can share one group when those bits match. The lab makes that overlap visible.

Interface identifiers and address configuration

The lecture teaches a 64-bit interface identifier (IID) and shows how to derive a modified EUI-64 from a 48-bit MAC address. Treat this as the source's conversion method, not as a rule that every modern host uses. Current recommendations advise against embedding a stable link-layer address in a stable IID; implementations can use stable opaque or temporary identifiers instead (RFC 8064). The lecture also emphasizes privacy addresses, multiple simultaneous addresses, and the difficulty of choosing a source address that matches routing and policy.

00-02-2D-02-82-34 → 00:02:2D | 02:82:34

The bar marks the insertion point after the first three octets.

Flip the universal/local bit

In the first octet, XOR with 0x02: 00 XOR 02 = 02. The bit is the second least-significant bit of the first octet (the universal/local bit).

Now the first half is 02:02:2D.

Insert ff:fe and regroup

Insert ff:fe between the halves: 02:02:2D:FF:FE:02:82:34.

Pair bytes into four 16-bit hexadecimal groups: 0202:2dff:fe02:8234.

Check: 8×8=64 bits. In a lab-style /64 address, this IID would fill the lower four hextets.

For the lecture's stateless autoconfiguration (SLAAC) story, a host first creates a link-local address and joins FF02::1. It sends an ICMPv6 Router Solicitation to the all-routers multicast address FF02::2. A router may answer with a Router Advertisement (RA). The RA's prefix information and flags allow the host to configure a suitable address; the RA also identifies router information used for a default route. The multicast membership is only how routers are reached, not where the prefix comes from. If no router answers, the host can still use link-local communication on that link. DHCPv6 and manual configuration are other methods.

The lecture's simplified example joins a 64-bit prefix to a 64-bit IID. /64 is the lab and common SLAAC arrangement, not a guarantee made by every RA. The source also points out that address autoconfiguration does not automatically supply every service setting (it names DNS, time, and WINS); those need their own configuration or discovery mechanism. For Neighbor Discovery detail, see RFC 4861.

The fixed base header and extension chain

IPv6's base header is always 40 bytes. The first six fields occupy 64 bits; the 128-bit source and destination addresses occupy 256 more bits, so the total is 320 bits, or 40 bytes. Payload Length counts the bytes after the base header and includes extension headers. Hop Limit is reduced at each forwarding router. The slide calls the eight-bit Traffic Class field “Class”; the current name and width are confirmed in RFC 8200.

Field order Size What to read
Version 4 bits Identifies IPv6 (value 6).
Traffic Class 8 bits Traffic handling / differentiated service marking.
Flow Label 20 bits Labels packets associated with a flow; it does not by itself guarantee QoS.
Payload Length 16 bits Bytes after the 40-byte base header, including extensions.
Next Header 8 bits Identifies the next extension header or upper-layer protocol.
Hop Limit 8 bits Forwarding lifetime; decremented by each router.
Source Address 128 bits Sending interface address.
Destination Address 128 bits Intended receiving interface or group.

The lecture's design contrast is a fixed base header, no base-header checksum, and no IPv4-style router-fragmentation fields. IPv6 routers do not fragment packets while forwarding; a source can fragment using a Fragment extension header. The fixed header makes the next parsing decision explicit rather than adding a variable-length base options field.

Base header: total width check

The Next Header field can name TCP/UDP directly or point to an extension header. That extension's own next-header value then continues the chain. The lecture's examples show base→TCP, base→Routing→TCP, and base→Security→Fragment→TCP/data. Its speaker notes explain the intended roles: Hop-by-Hop Options are examined along the path; a Routing header describes intermediate nodes; a Fragment header carries source-created fragments; Destination Options are for the destination; Authentication Header (AH) authenticates and protects integrity without confidentiality; ESP provides confidentiality and may also provide integrity/authentication. AH and ESP are IPsec mechanisms, not a promise that IPv6 traffic is automatically secure. Extension-header processing follows the protocol specification; avoid treating these slide descriptions as a deployment recipe.

QoS, security, and routing ideas retained from the lecture

The slide set links Traffic Class and Flow Label to special handling and quality of service. It also gives a historical priority scheme: values 0–7 are described as traffic that can back off and 8–15 as traffic that cannot. Examples include 0 uncharacterized, 1 filler/news, 2 unattended transfer/email, 4 attended bulk transfer, 6 interactive traffic, and 7 internet control; 3 and 5 are marked reserved. Treat this as the lecture's historical teaching model, not a modern service guarantee. The current header has a Traffic Class field; its marking is interpreted by network policy.

The routing slides say existing IPv4 routing algorithms can be reused and mention provider selection, mobility, and readdressing as possible IPv6-related functions. They motivate the capabilities but do not teach a new routing algorithm here; routing procedures belong on the routing page.

Coexistence: tunnel, ALG, and DNS answer different problems

IPv4 and IPv6 can coexist through dual-stack operation or by carrying IPv6 packets across an IPv4-only transit network. A tunnel places the entire IPv6 packet inside an outer IPv4 packet between tunnel endpoints. The IPv4 transit network forwards the outer packet and does not interpret the inner IPv6 extension chain. The extra outer header consumes MTU, so tunnel endpoints must account for the smaller effective packet size. See RFC 4213 for the lecture-era basic mechanisms.

An application-layer gateway (ALG) is different: it understands an application protocol and may need to translate embedded IP literals or application behavior. It does not wrap the whole IPv6 packet. DNS helps clients find addresses: an AAAA record (type 28) stores an IPv6 address, just as an A record stores IPv4. An AAAA record does not give an IPv4-only host direct IPv6 connectivity. Two DNS rules must be distinguished: NS, SRV, and MX queries can return both A and AAAA address records during additional-section processing; a query whose own type is AAAA does not itself trigger additional-section processing. The lecture's NS/MX rule is retained; RFC 3596 §§2.3 and 3 lists SRV in place of the slide's historical MB example.

Read the changing multicast memberships

Before overriding R1's link-local address, the sample G0/0 interface has a hardware-derived link-local IID FE80::D68C:B5FF:FECE:A0C0. Its displayed groups are FF02::1, FF02::1:FF00:1, and FF02::1:FFCE:A0C0. Those EUI-64 values depend on the interface MAC; they are samples, not expected universal values. Solicited-node membership uses the low 24 bits: the global address ending ::1 contributes 00:00:01, while the generated link-local suffix contributes CE:A0:C0.

After configuring FE80::1 on G0/0, its global and link-local addresses share the low 24 bits 00:00:01, so the displayed groups are FF02::1 and FF02::1:FF00:1. This is one shared multicast membership for two unicast addresses; neither unicast address disappears. Once ipv6 unicast-routing is enabled, FF02::2 appears because the router joins the all-routers group. PCs learn prefix and router information from Router Advertisements, not from the membership list itself.

Verify both links and diagnose a failed path

Use the lab's checks in order, so each result narrows the fault:

  1. On R1, run show ipv6 interface brief to confirm both global addresses and that G0/0 and G0/1 are up. Use show ipv6 interface g0/0 to inspect link-local, global, multicast groups, and MTU.
  2. On PC-B, run ipconfig before enabling routing and again afterward. The second view checks whether address configuration has arrived; the RA is the source of prefix and router data.
  3. From PC-A, ping FE80::1 on its local link, then ping S1 at 2001:db8:acad:1::b. If the first works but the second fails, check the SVI address, switch IPv6 support/SDM, and link state.
  4. From PC-A, run tracert 2001:db8:acad:a::3. The source trace has router hop 2001:db8:acad:1::1 followed by PC-B 2001:db8:acad:a::3. Then ping PC-A from PC-B and ping the local router link-local address FE80::1 from PC-B.

The lab screenshot's response times are sample observations, not required values. If a host has more than one interface, a link-local ping may need the platform's interface-scope syntax. If the routed test fails, check both /64 assignments, interface state, ipv6 unicast-routing, and each PC's gateway before interpreting the trace. The lab gives Cisco 1941/2960 hardware as a baseline and warns that other models and IOS versions can show different command output. Its starter credentials are classroom defaults, not secure deployment settings.

Common mix-ups

  • :: replaces one run of whole zero hextets, not arbitrary zero digits. Expand to eight groups to verify the result.
  • The first 64 bits are the prefix only when the prefix length is /64. A subnet-ID label needs the lab's /48 hierarchy assumption.
  • Link-local addresses work within a link and are not routed. The same text FE80::1 on two router interfaces refers to two link-scoped endpoints.
  • Joining FF02::2 lets a router receive router-directed multicast; it does not itself advertise a network prefix. The RA carries that information.
  • EUI-64 is the lecture's derivation example, not a universal present-day IID method.
  • IPv6 routers do not fragment in transit; sources may use the Fragment extension header.
  • AH is not encryption, ESP is not automatically present, and a Flow Label does not promise a QoS level.
  • A tunnel adds an outer packet around the entire IPv6 packet. An ALG handles application-specific content. An AAAA record maps a name to an IPv6 address; none of these should be described as the same kind of translation.

Quick check

Remember the 40-byte base header, one-use :: compression, link-local scope, the RA's role, and the distinction between tunneling, an ALG, and DNS. For binary prefix arithmetic beyond the lab's /48-to-/64 split, continue with IPv4 addressing and subnetting.
