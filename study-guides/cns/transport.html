Transport services and connections

How end-to-end transport delivers data to the right process, distinguishes service choices, and handles generic connection and buffer problems.

Big picture

The transport layer carries data from one end process to another. The network layer moves packets between hosts; transport adds the process-level service applications need and can improve on the service the network provides. It is an interface between applications and network delivery, while the data-link layer handles one link at a time.

The lecture also places fragmentation, multiplexing and inverse multiplexing, service selection, connection naming and lifecycle, and flow control among transport responsibilities. The assigned slides list fragmentation but do not teach a fragmentation procedure here, so this page keeps it at that scope. Layers 1–4 provide transmission toward an end host; layers 5–7 use that service, with transport acting as an important interface for application programmers.

From hosts to processes

An IP address identifies a host. A transport port identifies a service or endpoint on that host. The first deck calls the host-and-port transport address a TSAP. A server listens on a service port; a client addresses that port and normally uses its own source port. The server then passes the arriving connection or datagram to the responsible service process.

The decks list HTTP port 80, DNS port 53, and SMTP port 25. A URL may specify a service in advance; a well-known port, a portmapper, or an application can also identify the port. The lecture describes ports below 1024 as privileged in the traditional model and client ports as generally 1024 or above. That is the lecture's convention, not a claim that every modern system applies the same rule.

Each TCP segment or UDP datagram carries source and destination ports as well as the source and destination IP addresses. For IPv4, the source's four-field identifier has this theoretical number of address/port combinations:

232×216×232×216=296

This is a count of possible IPv4 address-and-port tuples from the slide's model, not a promise of that many usable simultaneous Internet connections.

Teaching example · reverse the endpoint fields in a reply

Suppose a request travels from 192.172.16.25:1026 to 203.115.22.54:25. For the reply, the server becomes the source and the client becomes the destination: source 203.115.22.54:25, destination 192.172.16.25:1026. The two port numbers do not change; their source/destination roles reverse with direction.

Multiplexing and demultiplexing

Transport can combine traffic from several application conversations for network delivery. At the receiving host, it separates arriving traffic and hands it to the intended process. The lecture pictures DNS and web traffic from several client windows to show this sharing; the picture illustrates the idea rather than specifying a full implementation lookup rule.

Do not confuse this with inverse multiplexing. The first deck uses a download accelerator as an example of one task using several network connections. Ordinary multiplexing combines several conversations; inverse multiplexing spreads one task across connections.

Choosing a transport service

The lecture presents service choices along three dimensions: connection-oriented or connectionless, reliable or not reliable, and unicast or multicast. Its protocol summary is:

Protocol Connection style Delivery properties in the lecture Destinations
TCP (Transmission Control Protocol) Connection-oriented Reliable transport service Unicast
UDP Connectionless Unacknowledged and not reliable at the transport layer Unicast or multicast

The source uses “Unreliable Datagram Protocol” in one slide, but the standards name is User Datagram Protocol. “Unreliable” describes the service contrast taught here; it is not the protocol's expansion. RFC 768 defines UDP and says delivery and duplicate protection are not guaranteed. An application that needs reliability may provide it itself. The assigned TCP section ends by deferring TCP to the next lecture, so this page does not expand that protocol into its later mechanics.

UDP is presented as useful for short messages when connection overhead is inappropriate. The lecture names VoIP, DNS, Sun Network File System (NFS), and remote procedure calls (RPC) as examples. Its header has four 16-bit fields:

Source Port Destination Port
UDP Length UDP Checksum

The four fields total 64 bits, or 8 bytes. In the encapsulation view, the UDP header and data sit inside an IP packet, which sits inside a data-link frame. The checksum helps detect corruption; it does not itself acknowledge, retransmit, or repair data.

Reliability: identify, check, track

The second deck frames the problem as delivering error-free data to the correct process. Its proposed pieces work together: a checksum helps check packet contents; IP addresses plus ports identify the endpoints; sequence numbers distinguish packets within a connection; and tracking packet status lets a sender learn whether delivery succeeded. Retaining sent copies matters when recovery may be needed. These are general transport functions here, not a description of a particular TCP recovery algorithm.

Connection establishment and stale messages

The service primitives are listen, connect, send, receive, and disconnect. In the basic service, the server listens, the client requests a connection, the server accepts, and then data can move in both directions. The lecture's detailed diagrams use generic messages—CR, ACK, DATA, and REJECT—because packets can be lost, delayed, or duplicated. They are not TCP flags or a TCP state machine.

The following walkthroughs preserve the slide's symbolic values x, y, and z. Each arrow is a message from the first host shown to the second; time moves downward.

Normal request, acknowledgment, and first data

1 · Request

Host 1 sends CR (seq = x) to Host 2. Host 2 has not yet confirmed this request.

2 · Accept

Host 2 replies ACK (seq = y, ACK = x). The acknowledgment refers to request value x; Host 2 uses y for its own sequence value.

3 · Begin data transfer

Host 1 sends DATA (seq = x, ACK = y). It refers to Host 2's y, completing the illustrated setup and beginning data transfer. The values are generic teaching labels, not TCP sequence arithmetic.

Rejecting an old CR that arrives later

Givens: The incoming request is an old duplicate, not a fresh user request. Sequence symbols describe this generic example only.

An old CR (seq = x) reaches Host 2 after its original context is no longer current.

2 · Host 2 responds

Host 2 sends ACK (seq = y, ACK = x), as shown in the generic scenario.

A duplicate CR (seq = x) reaches Host 2. Host 2 returns ACK (seq = y, ACK = x).

2 · Old data travels independently

The source draws an old duplicate DATA (seq = x, ACK = z) from Host 1 toward Host 2. Its acknowledgment z differs from the current response value y, so this packet does not acknowledge that response. The diagram does not specify a complete receiver acceptance rule.

3 · Host 1 rejects the unexpected setup response

The REJECT (ACK = y) arrow also runs from Host 1 to Host 2. It can answer the unexpected setup acknowledgment received by Host 1; it is not a receiver-side rejection of old DATA by Host 2. The drawing leaves the local decisions implicit. Keep those two events separate rather than infer a rejection rule from their placement. This is a generic duplicate-message illustration, not a TCP procedure.

Connection release and loss cases

The release goal is threefold: both sides agree the connection is closed, data is not lost, and neither side waits forever for the other. In the normal generic example, each side sends a disconnect request (DR). Host 1 releases after receiving Host 2's DR and sends the final ACK; Host 2 releases after receiving that acknowledgment. The source starts a timer at Host 1's first DR and at Host 2's reply.

These are generic transport-service examples. The deck does not name formal states or identify this DR exchange with TCP's close procedure.

Worked trace · normal three-message release

Both sides exchange DR and ACK

Givens: No messages are lost in this trace; each host releases after its indicated peer message.

1 · Host 1 requests release

Host 1 sends DR and starts its timer. Host 1 remains able to handle the peer's response while waiting.

2 · Host 2 responds

After receiving the request, Host 2 sends DR and starts its timer. The two sides have now both requested release.

3 · Host 1 acknowledges; Host 2 closes

Host 1 releases its connection and sends ACK. On receiving it, Host 2 releases too. This is the slide's normal three-message case: DR → DR → ACK.

Worked trace · final ACK is lost

Host 2 uses its timer when the final ACK disappears

Givens: The peer DR reaches Host 1; only Host 1's final ACK is lost.

1 · Both DR messages arrive

Host 1 sends DR and starts a timer. Host 2 receives it, replies with DR, and starts its own timer.

2 · Host 1 releases and sends ACK

Host 1 receives Host 2's DR, releases, and sends ACK. The network loses this final acknowledgment.

3 · Host 2 times out

Host 2 does not wait forever for the missing ACK. Its timer expires, so it releases the connection as shown in the source.

Worked trace · Host 2 response DR is lost

Host 1 retries its DR after timeout

Givens: The first response DR is lost; Host 1 retries after timeout; the later exchange is delivered.

1 · Host 2 response disappears

Host 1 sends DR and starts its timer. Host 2 receives it and sends DR, but the response is lost.

2 · Host 1 times out and retries

Host 1 receives no response before its timer expires, so it sends DR again and restarts the timer.

3 · Retry succeeds

Host 2 receives the repeated DR, sends DR again, and starts its timer. Host 1 receives it, releases, and sends ACK. Host 2 receives the acknowledgment and releases.

Worked trace · response and subsequent DR attempts are lost

Both sides eventually release by timeout

Givens: The initial Host 2 response and Host 1's subsequent DR retries are lost; each side has timeout behavior as drawn.

1 · Initial request reaches Host 2

Host 1 sends DR and starts its timer. Host 2 receives it, responds with DR, and starts its timer; the response is lost.

2 · Host 1 retries; retry is lost

Host 1 times out and retransmits DR, restarting its timer. This and subsequent attempts are lost as in the slide's case (d).

3 · Host 1 reaches its timeout limit

After the illustrated N timeouts, Host 1 releases. It cannot keep waiting indefinitely.

4 · Host 2 times out too

Host 2 eventually reaches its own timeout and releases. No final ACK is shown in this case. The teaching point is bounded waiting under repeated loss, not a guarantee that a lost release exchange delivered every control message.

Flow control and receiver buffering

The sender wants to send quickly, but the receiver has finite buffer space. The lecture's qualitative rule is to keep copies of sent data and avoid sending more than the receiver can currently hold if loss must be avoided. Sending beyond that capacity may be faster, but risks dropped data. This is receiver-buffer flow control in the lecture; it is not a quantitative window algorithm and should not be confused with congestion control.

Supplemental example · reason about a finite receive buffer

Eight buffer slots and a ten-unit message

Givens · teaching example: current free receiver buffer = 8 units; pending message = 10 units; no additional buffer mechanism is assumed.

1 · Compare message and available space

The receiver has room for 8 units; the sender has a 10-unit message. If it sends all ten immediately, two units exceed the known free space and may be dropped.

2 · Choose a no-overflow send

Sending at most 8 units stays within the stated capacity. The sender retains its copy of the remaining data and waits for delivery status or room before continuing.

3 · Check the decision

Check: 8 sent units fit 8 free slots; 2 units remain in the sender's copy. Sending all 10 at once would exceed capacity by 2, so it carries the drop risk described in the lecture. The numbers are a teaching example, not a protocol window field.

Quick revision and practice

  • Transport is end-to-end and delivers to processes; data link operates across one link.
  • A transport endpoint uses a host address and port. Direction determines which endpoint is source and which is destination.
  • Multiplexing combines application conversations; demultiplexing separates them at delivery. Inverse multiplexing uses several network connections for one task.
  • The assigned slides' connection messages are generic. Sequence information helps expose old duplicates; it does not make these TCP's actual handshake messages.
  • Release exchanges use timers in the illustrated loss cases so a host does not wait forever.
  • A checksum can detect errors; acknowledgment and recovery are separate ideas. UDP's checksum does not make UDP reliable.
  • Receiver-buffer flow control and network congestion control are different topics.
  • Quiz 1 Question 1's three-bit Go-Back-N result (7) belongs to link-layer ARQ, not a TCP window; see Data link framing, errors and flow control.

Check your answer

Port 53 selects the DNS service on the destination host. The client endpoint is identified by its host IP address and its source port; for the illustrated connection, the full flow also includes both destination fields.

In one sentence, distinguish multiplexing from inverse multiplexing.

Check your answer

Multiplexing carries several application conversations over transport/network delivery, while inverse multiplexing uses several network connections for one task, such as the lecture's download accelerator example.

Why does a receiver use sequence information in the old-duplicate examples?

Check your answer

It helps distinguish messages belonging to an earlier exchange from messages that match the current connection context, preventing a stale request or data message from being accepted as current.
