IPsec and TLS

Trace who terminates IPsec or TLS protection, what each packet mode authenticates or encrypts, and how the lecture’s TLS 1.0-era handshake sets up protected records.

Big picture

Secure-protocol questions become easier when you identify three things first: which endpoints terminate protection, which layer applies it, and which packet fields remain visible. IPsec protects IP traffic between hosts or gateways; TLS in this lecture sits over TCP and protects application records after a handshake. The focus here is protocol mechanics. For the short privacy, integrity, authentication, and cryptography reminder, see Security foundations; certificate trust is covered in Public key infrastructure.

Endpoints and layer placement

The slides show three connection choices. Direct hosts A and B communicate through the Internet, facing eavesdropping, imposters, and denial-of-service attempts. Observers can see ordinary IP headers needed for routing and may infer usage from them even when some content is encrypted. With a site-to-site tunnel, each internal network has a gateway; those gateways become the IPsec peers, while packets from internal host A to B travel inside the protected tunnel. A remote mobile user can instead terminate protected access at one gateway. The gateway controls access, may need to protect the user's identity, and must account for the user's changing address.

The protocol layer determines where protection begins and ends. Link-layer protection applies between adjacent devices. IPsec applies at the IP layer and can protect traffic across an internetwork. The lecture places SSL/TLS above TCP and below an application such as HTTP. Choosing one layer does not remove the need for a routable outer IP header.

IPsec state: Security Associations and replay

IPsec is presented as providing integrity, authentication, confidentiality, and access control at the IP layer. Which services an application needs depends on its risk: the lecture treats integrity and authentication as essential for protected applications, while privacy is not always justified. It names Authentication Header (AH) and Encapsulating Security Payload (ESP), each usable in transport or tunnel mode. It cites RFC 2401, RFC 2402, and RFC 2406 as the period's IPsec specifications. Those identifiers are historical: RFC 4301 explicitly obsoletes RFC 2401 and provides the later architecture (RFC 4301); the updated AH and ESP specifications are RFC 4302 and RFC 4303.

A Security Association (SA) is a negotiated, one-way arrangement between two network-layer entities. Its state identifies the association and records the selected services, algorithms, key-establishment approach, and lifetime. A bidirectional exchange therefore uses two SAs: one for each direction. A Security Parameters Index (SPI) carried in AH or ESP helps the receiver select the matching SA; it is an identifier, not the secret key itself.

Integrity checks detect whether protected packet data changed. Under the lecture's keyed-check model, binding the shared secret, sender or association context, and message can also support authentication. IP fields that may change in transit are not compared as if immutable: the source says they are set to zero during the calculation; the more precise AH wording is that mutable fields are normalized (often to zero) or treated according to their defined predictability (RFC 4302, mutable fields).

Integrity does not establish freshness. A valid packet copied by an attacker can still be a replay. The protected sequence number and receiver's replay window track packets already accepted and reject duplicates or packets too old for the window. The receiver checks the packet's selected integrity/authentication protection before accepting a fresh sequence value.

Assume 45 passes the integrity check. It is newer than 43, so accept and move the four-value window to [42, 43, 44, 45]. Values 44 and 45 were not previously accepted; 42 and 43 remain tracked.

Check an old packet

Sequence 40 is now below the window's lower edge 42, so reject it as too old. Independent check: duplicate 41 was rejected while still in range; 40 is rejected because advancing the window moved it out of range. Integrity alone would not detect either replay.

The lecture lists manual key setup, a Key Distribution Center, a Certificate Authority, and IKE as setup approaches. Its IKE note cites RFC 2409 and assumes peer identities plus pre-established secret material; preserve that as a historical lecture summary. RFC 9395 moves IKEv1 RFC 2409 to Historic status and records its deprecation; modern IPsec key exchange is specified by IKEv2 (RFC 7296). A CA can support identity credentials, but it is not itself the SA negotiation protocol.

AH: authentication and integrity without privacy

AH is inserted after IP headers examined at each hop and before the protected upper-layer content. In IPv4, protocol value 51 signals AH. Its fields, in order, are Next Header | Payload Length | Reserved | SPI | Sequence Number | Authentication Data. Next Header identifies what follows AH; Payload Length describes the AH length in 32-bit words under the format used in the slides; SPI selects the SA; the sequence number supports replay protection; Authentication Data contains the check result. Field-label correction: the slide describes Length as the authentication-data length. RFC 4302 defines Payload Len as the AH header length in 32-bit words, with the first two words subtracted from the encoded value (RFC 4302, AH format).

In transport mode, AH follows the original IP header. The receiver authenticates selected immutable IP fields and the following protected content; changeable fields are normalized or excluded. The data remains readable because AH does not encrypt it.

In tunnel mode, a new outer IP header routes between the AH peers, then AH covers the original inner IP packet. This gives authentication/integrity for the inner packet, but AH tunnel mode as drawn in the lecture does not make it private. The outer route remains visible; mutable outer fields are handled according to AH rules.

ESP: privacy, with optional separate authentication data

ESP's lecture format is SPI | Sequence Number | Payload Data | Padding | Pad Length | Next Header | optional Authentication Data. In IPv4, protocol value 50 signals ESP. SPI selects the SA and sequence number supports anti-replay. The format encrypts from Payload Data through Next Header, so the padding, Pad Length, and encapsulated protocol type are hidden. SPI, sequence number, and the outer IP header remain visible.

The slide makes the trailing Authentication Data optional. In this historical separate-ICV format, when it is selected, the check covers ESP from SPI through Next Header and excludes Authentication Data itself. That ESP check authenticates the ESP packet fields, including ciphertext when encryption is used; the outer IP header is outside that ESP span. Encryption alone does not prove integrity or sender authenticity. The format boundary is specified in RFC 2406 and its successor RFC 4303.

In transport mode, the original IP header stays outside ESP and remains visible; ESP protects the upper-layer content. In tunnel mode, ESP carries the whole original IP packet as encrypted content under a new visible outer IP header. The lecture also notes trusted routers may decrypt at a tunnel endpoint and route the recovered inner packet. AH and ESP may be combined, but AH is not a required precondition for ESP.

Teaching example: identify what a packet observer can read

Apply the four packet layouts to one request

Input: original packet IP(A → B) | TCP | request. For tunnel cases, IPsec peers are gateways G1 and G2. Assume ESP's separate Authentication Data option is enabled where its authentication span is discussed.

AH transport: insert an integrity header

Given an IPv4 packet A → B | TCP | request, place AH after the IP header: IP(A → B) | AH | TCP | request. AH protocol value is 51. The receiver checks the AH authentication data over the protected payload and selected immutable IP-header fields; mutable fields are normalized or excluded. Nothing is encrypted, so the addresses and request remain readable. Check: AH can reveal alteration, but it cannot hide the request.

AH tunnel: authenticate an encapsulated packet

Given the same original packet and gateways G1 and G2, wrap it as new IP(G1 → G2) | AH | original IP(A → B) | TCP | request. The original packet is authenticated. Selected mutable outer-header fields are normalized or excluded. Neither the new outer header nor the inner packet is encrypted. Check: the observer sees both routing endpoints and inner addresses/content.

ESP transport: protect upper-layer content

Start with IP(A → B) | TCP | request. Add ESP after the original IP header. In the lecture's format the result is IP(A → B) | ESP(SPI, sequence) | encrypted[TCP | request | padding | pad length | next header] | optional Authentication Data. The outer IP header, SPI, and sequence number stay visible. The next-header value is inside the encrypted span. If separate Authentication Data is enabled, its check covers the ESP packet from SPI through Next Header, excluding itself. Check: the original endpoint addresses remain visible while the upper-layer protocol and content are concealed.

ESP tunnel: protect the complete original packet

Wrap the original packet as new IP(G1 → G2) | ESP(SPI, sequence) | encrypted[IP(A → B) | TCP | request | padding | pad length | next header] | optional Authentication Data. Internet routers see G1 → G2 and the ESP header fields; they cannot read the inner A → B header or request. The receiving gateway verifies the selected protection, decrypts, recovers the original packet, and forwards it internally. Check: only the new outer IP header is needed for routing across the tunnel.

SSL/TLS above TCP: handshake state and protected records

The slides place TLS Record over TCP and IP, with Handshake, Change Cipher Spec, Alert, and application protocols such as HTTP carried above the Record layer. The stack applies beyond HTTP; the slides also name FTP, Telnet, e-commerce, and email. SSL was developed by Netscape; the deck describes SSL 3.0 as submitted to the IETF and TLS as standardized in RFC 2246 with “slight differences.” Correction and version boundary: RFC 2246 is specifically TLS 1.0 (1999), not a definition of all TLS versions. TLS 1.0 and TLS 1.1 were later formally deprecated by RFC 8996; use RFC 9325 for secure-use recommendations. The historical details below describe the lecture's TLS 1.0-era model, not a TLS 1.3 lesson or current configuration advice.

The Handshake negotiates a protocol version, encryption and key-generation choices, can authenticate peers with public-key mechanisms, and establishes shared secret state. The slide does not provide a message-by-message handshake transcript, so the sequence below shows the responsibilities in order, not exact TLS wire messages. Multiple secure connections may be associated with a session under the old resumable-session model.

The lecture lists these TLS 1.0-era session fields: Session Identifier (server-selected byte sequence), peer certificate, compression method, cipher spec (encryption and MAC), 48-byte Master Secret, and a resumable flag. RFC 2246 confirms this parameter list and the master-secret size (RFC 2246, session state). These are version-specific fields and mechanisms; do not generalize them across TLS generations.

The Record Protocol carries protected data over TCP. In the slide's older design, negotiated symmetric encryption provides privacy and a separate keyed MAC protects record integrity/authentication. The slide calls that MAC a “reliability service,” but that wording conflates two jobs: a MAC detects unauthorized modification under the negotiated key; TCP provides reliable ordered byte transport (RFC 793). The slide says record data is handled without the hash only during session negotiation. The other named control protocols—Change Cipher Spec and Alert—are carried above Record in the stack; the lecture does not describe their wire transitions or message sequence. Modern TLS record protection differs, so the separate-MAC model is kept historical here.

Teaching example: follow setup into a protected application record

Separate handshake work from record work

Version scope: lecture-era TLS 1.0 model based on RFC 2246. This is a conceptual procedure, not a full wire trace.

Start with transport

Givens: a client sends an application request to a server using the lecture's TLS-over-TCP stack. TCP connection setup is complete.

TCP is below TLS Record and carries the TLS byte stream.

Negotiate session parameters

The client and server use Handshake to agree on protocol version, cipher spec, and key-generation method. The server presents its certificate; the client validates identity as required. The lecture says either peer may be authenticated when configured.

Establish the shared secret

The handshake establishes shared secret state. In the TLS 1.0-era model, the session records the 48-byte Master Secret and other listed parameters; connection-specific record keys are derived from the negotiated state.

Protect the application bytes

The client passes request bytes to TLS Record. Under the old slide model, the record is encrypted for privacy and protected by a keyed MAC for integrity/authentication, then carried by TCP. The peer checks the record protection before delivering the recovered bytes to its application.

Check the division of labor

Handshake: agree, authenticate as required, and establish secrets. Record: protect and carry data. TCP: reliable ordered byte transport. The diagram's labels are conceptual roles, not a transcript of handshake messages.

Independent check: the keyed MAC does not retransmit lost bytes; TCP does.

Common confusions

  • AH versus ESP: AH authenticates selected fields without encryption. ESP encrypts its defined content span and can add separate authentication data.
  • Transport versus tunnel: transport keeps the original IP header visible; tunnel adds a new outer IP header and places the original packet inside.
  • Visible outer header: even ESP tunnel traffic needs gateway addresses so routers can forward it.
  • SPI versus sequence number: SPI selects an SA; sequence state helps reject replays.
  • Integrity versus freshness: a valid check can belong to an old copied packet, so the replay window matters.
  • TLS Handshake versus Record: Handshake sets the negotiated state; Record protects carried data.
  • TLS MAC versus TCP reliability: the slide's MAC wording is inaccurate; TCP handles reliable ordered delivery.
  • Historical field lists: RFC 2246 details belong to TLS 1.0 and should not be treated as universal TLS behavior.

Quick review

For a protocol scenario, name the peer endpoints, identify the layer and mode, then mark (1) visible routing fields, (2) authenticated fields, and (3) encrypted fields. For a TLS question from these slides, state the TLS 1.0-era scope, separate Handshake responsibilities from Record protection, and keep TCP's delivery role distinct from a MAC.

Practice

A valid packet with sequence number 41 arrives, but 41 was already accepted. What rejects it?

Check your answer

The receiver replay window marks 41 as already accepted. The packet can have a valid integrity check and still be stale.

How many SAs carry protected traffic in both directions between G1 and G2?

Check your answer

Two: one simplex SA for G1 → G2 and one for G2 → G1.

In ESP tunnel mode, which address pair remains visible across the Internet?

Check your answer

The new outer gateway addresses. The original host addresses are inside the encrypted original packet.

Does AH tunnel mode hide or encrypt the original packet?

Check your answer

No. AH authenticates the original inner packet but does not encrypt it; the inner header and content remain readable.

In the lecture ESP layout, which fields are encrypted and which help choose/check the SA?

Check your answer

Payload Data through Next Header is encrypted. SPI selects the SA and the sequence number supports anti-replay; both remain outside the encrypted span.

What does the lecture-era TLS Handshake establish, and what does Record do afterward?

Check your answer

Handshake negotiates parameters, authenticates peers as required, and establishes shared secrets. Record uses the negotiated protection to carry application data.
