Security foundations and cryptography

Security starts by deciding what must be protected, identifying who or what could threaten it, and matching each requirement to a control that actually provides it.

Big picture

A computer system is dependable when it behaves as expected. Security protects the resources that make that possible: physical equipment, data and software, people, and trust. Connecting systems creates useful services, but it also exposes hosts and communications to parties outside the owner’s control. A useful way to reason about security is to move from asset, to threat, to required property, to control—then ask what the control still leaves exposed.

The lecture’s scope runs from individual computers to networks and web use. The companion protocol lecture begins with the same foundations, then turns to protocol details. This page keeps those foundations together; use Public key infrastructure for certificate trust and pairwise key-count questions, and IPsec and TLS for packet protection, protocol modes, and historical handshake details.

Assets, exposure, and risk

Security is not simply “block everything.” Denying all access would protect a system by making it useless. The task is to allow the work that is needed while reducing avoidable exposure. A threat may come from an insider (such as a user or administrator) or an outsider (such as a contractor, former employee, or unknown attacker). The lecture’s broad statement that most incidents are caused by insiders is not a universal statistic; the practical lesson is to include both trusted and untrusted actors in the threat model.

Network risk grows harder to control as systems become dispersed, heterogeneous, and independently managed. Hardware and software differ; some nodes may be invisible to a single administrator; and Internet reachable services can be probed by people the owner does not know. Vulnerabilities may be discovered before the owner can react. The system boundary includes ordinary hosts and network equipment such as servers, workstations, routers, and switches.

Asset to protect Example exposure Security question
Physical assets Unauthorised access to a device, cable, or outlet Who can reach or alter it?
Data and software Disclosure, modification, deletion, or malicious code Who may read or change it?
Personnel Deception or unsafe access decisions What evidence supports the request?
Trust and service Impersonation or an unavailable service Is this the expected party, and can the service still work?

System attacks often follow two broad paths: an attacker impersonates a valid user (for example through social engineering, wiretapping, or searching for exposed information), or exploits a defect in hardware, an operating system, or an application. Both matter: good access rules do not fix a vulnerable service, and software updates do not establish who is requesting access.

Reduce avoidable host and network exposure

Provide only the services a host needs and keep those services maintained. Minimise unnecessary components because each component and interaction can contain defects. Use maintained components, enable their security features, apply operating-system and application updates, and monitor relevant security notices. No system is completely safe, so prevention needs a recovery plan as well.

Protect servers, clients, and network infrastructure. Client machines are shaped by user choices and installed software; explain safe use and control unnecessary software where appropriate. Switches, routers, cabling, and physical outlets need protection too. A wide-area network may be outside the local organisation’s control, which makes endpoint protections and secure communication important.

The lecture contrasts Internet connections to one dial-up computer, dial-up access shared by a network, and a dedicated network connection. The practical distinction is how much of the local environment is exposed: connecting one host still exposes that host, while connecting a network brings more hosts and services within reach. Internet access works in both directions—local users can reach outward, and remote parties can attempt to reach services inward.

Web security has at least three separate locations: the server and its application/database boundary, the browser and its features, and the information travelling between them. Downloaded files (including signed files, which can help identify a publisher), helper applications, plug-ins, JavaScript or Java execution, ActiveX, cookies, and browser defects create different risks at the client. These are the lecture’s examples, some from its period; the durable lesson is that a large, feature-rich client has an attack surface of its own. An encrypted channel protects data in transit; it does not repair an unsafe browser, secure a compromised server, or protect data after it reaches an endpoint. The lecture names SSL as an encrypted-web example and contrasts 40-bit and 128-bit export-era encryption. Both are historical framing, not current configuration guidance. SSL is historical, and SSLv3 is prohibited by RFC 7568. Current TLS mechanics are covered in IPsec and TLS.

Security goals and access decisions

In the lecture’s historical SSL description, the encrypted browser-server channel identifies the server; identifying the user is optional and described as uncommon. The stated 40-bit and 128-bit export-era key lengths and the warning to consider software-vendor trust are period context, not modern settings.

The lecture presents “security holes” as possible usability trade-offs as well as defects: a control that denies every action makes a system unusable. For network access, it also names manual, computer-based, time-based, and smart-card challenge-response variants without specifying their algorithms here.

Security requirements describe what a system should preserve. Confidentiality (called privacy in the companion lecture) limits who can read information. Integrity lets a recipient detect unauthorised change. Authentication checks a claimed identity. Availability keeps information and services usable. Accountability records actions so they can be attributed; non-repudiation is stronger evidence intended to prevent a sender from plausibly denying a message. These goals connect, but they are not interchangeable.

Requirement What it answers Typical concern
Confidentiality / privacy Who can read the information? An observer reads a transaction
Integrity Was the information changed without detection? An intermediary modifies a request
Authentication Is the party who it claims to be? A client or server is impersonated
Availability Can an authorised user obtain the service? A server is overwhelmed
Accountability / non-repudiation Can an action or message be attributed and later supported as evidence? A party denies having sent a message

Access control is the system’s front door. Identification names an account; authentication checks evidence for the claimed identity; authorisation decides what that authenticated account may do. Authentication evidence can be something possessed (such as a token), known (such as a password), or inherent (such as a fingerprint). A password sent as readable plaintext can be observed on a network, so the lecture points to cryptographic access mechanisms such as SSH and challenge-response.

After authentication, apply minimum privilege: give each role only the permissions it needs. File and directory permissions can separately allow or deny reading, writing, modifying, and deleting for a user or group. This is more useful than a single “trusted/untrusted” label because a person may need to read one file but not delete it.

Threats and controls

An attack is easier to understand when its path is explicit. A passive observer records traffic; a replay attacker later resends a captured request. An imposter pretends to be a client or server. A man in the middle relays and may alter messages while misleading both endpoints. A denial-of-service attacker consumes resources so legitimate users cannot get service. A virus inserts copies of itself into other programs when executed; a worm installs copies on other networked machines. Malware can harm privacy, integrity, and availability.

ThreatWhat happensMain property at riskControl direction
Eavesdropping and replayTraffic is recorded; a captured request may be sent againPrivacy, authentication, and freshnessProtect the channel; authenticate and reject stale/reused requests
Client imposter / source spoofingA requester claims to be an authorised clientAuthentication and confidentialityAuthenticate the client; a source IP address alone is not identity proof
Server imposterA false service solicits a user’s secretsAuthentication and confidentialityAuthenticate the server before trusting it
Man in the middleAn intermediary relays messages and may change themAuthentication and integrityAuthenticate endpoints and protect message integrity
DoS / DDoSOne or many machines flood a service until resources are exhaustedAvailabilityBorder controls and service-side capacity/response measures
Virus or wormMalicious code runs, copies itself, or spreads to other systemsPrivacy, integrity, and availabilityEndpoint controls, careful execution, updates, and detection

The companion lecture lists channel protections—encryption, cryptographic checks, authentication, and signatures—and border protections such as firewalls, malware checking, intrusion detection, authentication, and access control. A firewall separates networks with different trust levels. It can deny inbound or outbound access, allow selected services, log attempts, and raise alerts. Packet filters inspect network-layer traffic; application gateways mediate application traffic. Rules need ongoing maintenance as services and risks change.

Firewall boundary: a perimeter rule can restrict which network traffic reaches a service, but an allowed request still needs server-side authentication and authorisation. A firewall is one layer in a system, not a cure-all.

Cryptographic language and two historical ciphers

Encryption transforms readable plaintext into ciphertext; decryption recovers plaintext. A cipher is the algorithm, and a key selects or parameterises the operation. The companion lecture uses two tiny examples to make the distinction between substitution and rearrangement concrete. They are teaching examples, not secure ciphers.

Worked source examples: reverse substitution and adjacent transposition

The original examples are hvxfirgb → security and security → esuciryt. The first uses the reverse-alphabet mapping; the second swaps each adjacent pair. Step through the mapping instead of treating the output as a memorised answer.

Trace the two source cipher transformations

Given: reverse-alphabet substitution abcdefghijklmnopqrstuvwxyz → zyxwvutsrqponmlkjihgfedcba; adjacent transposition swaps each pair. Source values: hvxfirgb and security.

1 · Reverse alphabet: map the first ciphertext letter

The reverse alphabet pairs a↔z, b↔y, c↔x, and so on. For h, the paired plaintext letter is s. The remaining ciphertext is vxfirgb.

2 · Continue the reverse-alphabet substitution

Map each letter through the same table: v→e, x→c, f→u, i→r, r→i, g→t, and b→y. Reading the result gives security. Check: applying the reverse-alphabet map again returns hvxfirgb.

3 · Adjacent transposition: split into pairs

The plaintext security is grouped as se | cu | ri | ty. The stated rule swaps positions k and k+1, so each pair reverses without changing its letters.

4 · Swap each pair and check

se→es, cu→uc, ri→ir, ty→yt. Join the pairs: esuciryt. The letter multiset is unchanged; only the order changed. This matches the slide’s ciphertext exactly.

Substitution preserves positions but changes symbols; transposition preserves symbols but changes their positions. The lecture notes that substitution can be attacked by comparing ciphertext letter frequencies with language frequencies, while known plaintext and ciphertext can expose a simple transposition mapping. These examples show why an algorithm that looks obscure is not necessarily secure.

Shared-key encryption and fresh challenges

The source’s criteria for a good cipher are practical implementation and deployment, a key space large enough to make trying every key infeasible, and resistance to key recovery even when an attacker knows many plaintext/ciphertext pairs.

In shared-key cryptography, both parties know the same secret key K. The sender computes ciphertext C=EK(P) from plaintext P; the receiver applies the inverse operation D_K with the same key. Correct decryption checks the relation DK(EK(P))=P. The source names DES, Triple DES, and AES as examples of key-based ciphers; this list is historical, not a recommendation to use them interchangeably today. NIST withdrew DES and no longer permits TDEA/3DES encryption after 2023; AES remains a standard block-cipher family. See NIST’s DES withdrawal and TDEA status.

Encryption can hide message contents, but encryption alone does not prove that ciphertext is authentic or unaltered. A modified ciphertext does not reliably become recognizable “gibberish.” Use a correctly constructed message authentication code (MAC) for keyed integrity, or an authenticated-encryption construction when both confidentiality and integrity are required. NIST explicitly distinguishes encryption from authenticity and describes authenticated-encryption modes in its confidentiality-mode guidance.

Worked source procedure: decrypt with the shared key

Follow plaintext through shared-key encryption and decryption

Given: a shared secret K, plaintext P, encryption E_K, inverse decryption D_K. No source numeric values are provided.

1 · Sender and receiver share K

The source assumes both parties already possess the same secret K. The sender starts with plaintext P. No numeric key or cipher arithmetic is supplied, so keep the example symbolic.

2 · Encrypt the message

Apply the keyed encryption mapping: C=EK(P). The transmitted value is ciphertext C; a passive observer should not learn P from it when the cipher and key are secure.

3 · Receiver decrypts

The receiver applies the inverse mapping using the same key: DK(C). Since C=EK(P), the result should be DK(EK(P))=P.

4 · Check what this establishes

Recovering P demonstrates the encryption/decryption relationship. It does not by itself show that the ciphertext was not modified or prove which person sent it. A separate authenticated check is needed for integrity/authentication.

The source’s mutual challenge-response figure has both endpoints demonstrate possession of the shared key. A nonce is a fresh value intended for one use. The recipient sends a challenge; the other endpoint returns a keyed transformation; the recipient checks it. Then the direction reverses. Fresh challenges make an old response unsuitable for a new challenge, assuming challenges are fresh and the cryptographic operation is sound. This proves possession of the shared key in that exchange; it does not independently establish a person’s real-world identity unless the key is securely bound to that identity.

Trace mutual shared-key challenge-response

Given: Jane and John share K; Jane chooses challenge r, John chooses a distinct challenge r′. The source’s figure shows r → E_K(r) and then r′ → E_K(r′) in opposite directions.

Opening claim: John first tells Jane ‘let’s talk,’ identifying himself. This claim alone does not authenticate John; the challenge and keyed response test possession of the shared key.

1 · Jane challenges John

Jane sends a fresh random value r to John. This is the challenge currently awaiting a response.

2 · John answers Jane’s challenge

John computes EK(r) with the shared secret and sends it back. Jane decrypts or otherwise verifies the response; it must correspond to her outstanding r. A previously recorded answer to a different challenge should fail this check.

3 · John challenges Jane

To authenticate the opposite direction, John sends a new challenge r′. It is a separate fresh value, not a reuse of r.

4 · Jane answers and John checks

Jane returns EK(r′). John verifies it against the challenge he just issued. Now each direction has been checked.

Keyed integrity checks

A keyed check attaches evidence that depends on both the message P and shared secret K. The source labels the output HK(P): the sender computes a fixed-length check, sends it with the message, and the receiver recomputes the check from the received message and compares the results. If they differ, the receiver rejects the message as changed or invalid. Because the check is keyed, a party without K should not be able to create a valid one. This is the conceptual role of a MAC; the lecture does not specify a deployable hash construction.

An unkeyed digest can detect accidental change when the digest itself is trusted, but an attacker who can replace both a message and its unkeyed digest can make the pair match. A keyed check addresses that threat when keys are protected and the MAC is properly designed. Neither an unkeyed hash nor a shared-key MAC alone provides public proof that one particular individual sent a message; non-repudiation requires a different trust and signature model.

The companion slides mention MD5’s 128-bit digest, 512-bit processing blocks, SHA-1’s 160-bit digest, and an ad-hoc keyed-MD5 idea. These are historical descriptions, not implementation advice; do not copy the key-append construction as a MAC. NIST advises transition away from SHA-1 toward SHA-2 or SHA-3, and RFC 6151 says MD5 is no longer acceptable where collision resistance is required. Modern keyed constructions include standard HMAC or a vetted MAC, not a home-made key concatenation.

Check a message with a keyed integrity value

Given: sender and receiver share secret K; message is P; the source’s keyed-check diagram sends P alongside HK(P). No algorithm-specific output is supplied.

1 · Sender computes a keyed value

For message P and shared secret K, compute t=HK(P). The check depends on the contents and the secret.

2 · Send message and check together

Transmit the pair (P, t). A change to the message should change the recomputed keyed value, while a party without K should not be able to make a valid replacement check.

3 · Receiver recomputes

On receipt, calculate t′=HK(Preceived) using the same protected key and the received message.

4 · Compare and decide

If t′=treceived, accept the message as passing this keyed integrity check. If they differ, reject it. The check does not hide P; add encryption separately if confidentiality is also required.

Public-key confidentiality and identity binding

Public-key cryptography uses a related public/private key pair. For confidentiality, anyone can encrypt a message to the recipient with the recipient’s public key K1; only the matching private key K2 should decrypt it: C=EK1(P) and P = D_K₂(C). This is the direction shown in the lecture figure. A public key must be verified as belonging to the intended recipient; otherwise an attacker can substitute a different key. Certificate trust and validation belong to Public key infrastructure.

The old slide also describes “encrypt with the private key, decrypt with the public key” as integrity. Treat that as an analogy, not the definition of a digital signature. Signature schemes have specific signing and verification operations, and a signature does not make a message confidential. The protocol page discusses where signatures are used; the PKI page explains how a public key is bound to an identity.

Trace the public-key direction for confidentiality

Given: intended recipient has public key K1 and corresponding private key K2; sender wants to protect plaintext P. The lecture supplies symbolic equations, not numeric cipher values.

1 · Recipient publishes K₁ and protects K₂

The intended recipient makes public key K1 available and keeps matching private key K2 secret.

2 · Sender encrypts for that recipient

The sender computes C=EK1(P). The operation is directed to the holder of the matching private key.

3 · Recipient decrypts

The recipient computes DK2(C)=P. The private key is needed to recover the plaintext.

4 · Verify the identity dependency

This reasoning only protects the intended recipient if K1 is actually that recipient’s public key. A substituted key changes who can decrypt. Check the certificate and trust chain on the PKI page; public-key encryption alone does not prove who sent P.

Common mistakes

  • Mixing integrity with identity. Integrity concerns unauthorised change; authentication checks a claimed identity; accountability links actions to actors. One does not automatically prove the others.
  • Assuming encryption detects tampering. Encryption alone can hide content without authenticating it. Use authenticated encryption or a properly constructed MAC when integrity is required.
  • Treating an IP address as an identity. A packet can carry a spoofed source address; authenticate the communicating party with an appropriate mechanism.
  • Treating a firewall as endpoint security. A firewall filters at a boundary. An allowed service can still have a vulnerable application or weak account permissions.
  • Replaying a valid old response. A challenge-response must use fresh challenges and check that a response answers the current outstanding value.
  • Using the wrong public-key direction. For confidentiality, encrypt to the recipient’s public key and decrypt with the recipient’s private key. Confirm that the public key belongs to that recipient.
  • Calling toy ciphers secure, or reusing historical hash constructions. The examples explain transformations only; the slides’ keyed-MD5 construction and obsolete algorithms are not current guidance.

Exam focus

  1. Name the asset, threat, security property, and control in a short scenario.
  2. Distinguish identification, authentication, and authorisation; apply minimum privilege to file operations.
  3. Match eavesdropping, replay, client/server imposters, man-in-the-middle, DoS, viruses, and worms to their effects.
  4. Explain the difference between substitution and transposition using the exact source examples.
  5. Trace C=EK(P) and DK(EK(P))=P, then state what encryption does and does not establish.
  6. Trace both directions of challenge-response and explain why the challenges must be fresh.
  7. Recompute and compare a keyed integrity value; distinguish it from encryption and an unkeyed digest.
  8. For public-key confidentiality, encrypt with the recipient’s public key and decrypt with that recipient’s private key; explain why identity binding matters.
  9. State what a firewall can filter or record and why hosts, clients, applications, and recovery still need attention.

Practice questions

A user can log in, but should only read one directory and never delete its files. Which security concepts govern these decisions?

Check your answer

Authentication checks the user’s claimed identity. Authorisation and file permissions grant read access while withholding delete permission. Minimum privilege says to provide only the access needed.

A captured request is sent again later. What happened, and what property should a protocol check?

Check your answer

This is replay after eavesdropping. The protocol should authenticate and integrity-protect the request and use freshness or anti-replay handling so an old request is not accepted as new.

Does encrypting a message with a shared key prove it was not changed?

Check your answer

No. Encryption alone does not assure authenticity. Add a correctly constructed keyed integrity check or use authenticated encryption; decrypting to unexpected data is not a dependable tamper test.

In the source substitution example, decode hvxfirgb. Then explain why security → esuciryt is a different cipher type.

Check your answer

The reverse-alphabet map gives h→s, v→e, x→c, f→u, i→r, r→i, g→t, b→y, so the result is security. The second example swaps adjacent character pairs, preserving the letters while rearranging their positions: se|cu|ri|ty → es|uc|ir|yt.

Why is encrypting to Bob’s public key not proof that Alice sent the message?

Check your answer

Anyone with Bob’s public key can encrypt to him. This operation protects confidentiality for Bob but does not authenticate the sender. Sender authentication/signature handling and trustworthy key binding are separate concerns.

A flood of requests prevents normal clients from receiving responses. Which goal is primarily affected, and can a border firewall solve every cause?

Check your answer

Availability is primarily affected. A firewall can restrict or log some traffic, but it is not a cure-all; service and endpoint protections remain necessary.
