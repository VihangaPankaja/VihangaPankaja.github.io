IP packets, ARP, ICMP, DHCP and NAT

Follow an IPv4 datagram from its header to a local or routed link, then see how ARP finds the next-hop MAC address, ICMP reports network conditions, DHCP configures a joining host, and NAT tracks replies to translated traffic.

Big picture

IP identifies the source and final destination of a datagram across networks. A link frame carries that datagram only to the next device on the current link. Routers use the destination network to choose an outgoing interface; ARP finds that link's next-hop MAC address. ICMP reports network-layer errors and queries, DHCP supplies initial configuration, and NAT keeps a translation record so replies to a shared public address reach the correct private endpoint.

Read the IPv4 datagram header

The header tells routers and destinations how to handle a datagram. It includes addressing, lifetime, payload selection, optional fragmentation information, and an error check for the header. The lecture calls the 8-bit service field “Type of Service” (ToS); modern IPv4 uses the DS field, with DSCP and ECN bits. The picture below preserves the source's field layout while correcting the IHL unit.

IHL is measured in 32-bit words: the minimum value 5 means 20 bytes, and the 4-bit field permits at most 15 words (60 bytes). Options, when present, are padded to a 32-bit boundary. Total Length is the number of octets in the whole datagram, header plus data. The three flag bits are reserved, Don't Fragment (DF) and More Fragments (MF); the 13-bit offset locates a fragment's data in 8-byte units. These fields support fragmentation and reassembly, but the lecture gives no fragmentation algorithm or worked fragment calculation, so none is inferred here. See RFC 791 §3.1. The historical ToS byte was redefined as the DS field by RFC 2474; ECN uses bits in this field as specified by RFC 3168.

The Protocol field identifies what receives the data next, such as TCP, UDP or ICMP. TTL limits how far a datagram can travel; in ordinary forwarding a router reduces it and recomputes the IPv4 header checksum. That checksum covers only the IPv4 header, not transport data. For the complete IPv4 addressing, subnet and VLSM calculations, see IPv4 addressing, subnetting and VLSM.

Choose direct delivery or a router

A sender compares the destination with its configured local prefix. If it is local, the destination host is the next hop. Otherwise, the forwarding table supplies a router next hop. Prefix arithmetic is covered in IPv4 addressing; path selection and routing methods are covered in Network layer and routing.

Direct delivery and the routed next hop

Source topology: A 223.1.1.1, B 223.1.1.3, E 223.1.2.2; router interfaces 223.1.1.4 and 223.1.2.9. Link-layer MAC values are deliberately left unspecified.

A sends to B on the same network

Givens: A is 223.1.1.1; B is 223.1.1.3. A's forwarding information says 223.1.1.x is directly connected, so A selects B itself as the next hop. If B's MAC is not cached, A resolves 223.1.1.3 with ARP. The Ethernet frame goes to B's MAC. The IPv4 source and destination remain 223.1.1.1 and 223.1.1.3; no router hop is taken.

A sends to E on another network

Change the destination to E, 223.1.2.2. A looks up the destination network and selects next hop/router interface 223.1.1.4. A resolves that local gateway IP to a MAC address, then sends a frame to the router's MAC. The packet still has source 223.1.1.1 and destination 223.1.2.2: the remote host's MAC is not needed on A's link.

The router forwards from interface 223.1.2.9

Router interface 223.1.1.4 receives the frame and checks its forwarding table. Network 223.1.2.x is directly attached through interface 223.1.2.9, so the router sends a new frame toward E, resolving E's MAC on that link if needed. It decreases TTL and updates the IPv4 header checksum. The IP source and destination normally remain A and E while the link frame and its MAC addresses change.

Check the endpoint and hop fields

At E (223.1.2.2), the destination IP is still E. The source IP is still A in ordinary routing. The outgoing Ethernet destination on the last link is E's MAC; the first link's destination was the router's MAC. A router also decreases TTL and recomputes the IPv4 header checksum. Fragmentation, if required and permitted, can change additional header fields; this example does not calculate or prescribe a fragmentation procedure.

The slide says the datagram “remains unchanged.” Interpret this narrowly: ordinary forwarding normally preserves the source and destination IP addresses, while link-layer framing changes at each link. TTL and the header checksum change at a router; fragmentation can change additional header fields. NAT is another case in which addresses and transport identifiers are deliberately translated. See RFC 791 and RFC 1812 §5.3.1.

Resolve the link-layer next hop with ARP

Knowing an IP destination is not enough to construct an Ethernet frame. ARP asks the local link which MAC address owns an IPv4 address. The address being resolved is the next hop selected by forwarding: a local destination's IP, or the gateway's IP for a remote destination.

ARP: resolve the selected next hop

Remote example: A 223.1.1.1 sends toward E 223.1.2.2. A's next hop is router 223.1.1.4. ARP target: 223.1.1.4.

Decide which IP needs resolution

For A → B on the same network, resolve B's IP (223.1.1.3). For A → remote E (223.1.2.2), the route selects gateway 223.1.1.4, so resolve the gateway IP instead. ARP answers the local-link question; it does not find a remote host across routers.

Broadcast the request on this link

A sends an ARP request in a link-layer broadcast asking who owns the selected next-hop IPv4 address. Devices on that local broadcast domain can receive it. Routers do not forward this Ethernet broadcast onto other routed links.

The owner replies; A can send the frame

The device that owns the requested IP replies with its MAC address. A can now put that MAC in the destination field of the outgoing link frame and cache the mapping for later use. The IPv4 destination remains the final host's IP, even when the frame is addressed to a router.

Check the mapping and keep the tables separate

Before sending, confirm the ARP cache gives a MAC for the selected next-hop IP; that MAC becomes the frame destination. For remote E, the selected next hop is gateway 223.1.1.4, while the packet's final IP destination stays 223.1.2.2. In Lab 1.1's sample, show arp pairs IP 192.168.1.3 with MAC 5c26.0a24.2a60; the switch MAC table separately learns that MAC on Fa0/6. The first is an IP-to-MAC cache; the second is a MAC-to-switch-port table. These are sample identifiers, not universal device values.

ARP resolves a protocol address to a local hardware address so a frame can be sent on the connected link (RFC 826).

Lab 1.2 reinforces the distinction by clearing dynamic switch MAC entries, waiting, then generating traffic and comparing arp -a with show mac address-table. ARP caches map IP to MAC; switches learn source MAC to local switch port. The broader MAC-learning labs and their switch behavior belong in LAN, Ethernet and switching. The routed host-to-host lab likewise uses a gateway between different /24 networks; its full configuration stays with routing.

ICMP reports network conditions

ICMP is carried as an IPv4 payload (IPv4 Protocol value 1). It is often described as “above IP” because it reports on IP delivery, but it is not a transport protocol like TCP or UDP. An ICMP message has a type and code: the type identifies a broad message, while the code gives a more specific reason.

Type Code Example meaning
8 0 Echo Request (ping)
0 0 Echo Reply (ping)
3 0 Destination network unreachable
3 1 Destination host unreachable
3 2 Destination protocol unreachable
3 3 Destination port unreachable
3 4 Fragmentation needed and DF set; relevant to path MTU discovery
11 0 TTL exceeded in transit
12 0 Parameter problem / bad IP header
9 0 Router Advertisement (historical router discovery message)
10 0 Router Solicitation (historical router discovery message)

The slide's type 9/10 labels use “route advertisement” and “router discovery”; RFC 1256 names them Router Advertisement and Router Solicitation. In a classic ICMP error, the quoted packet includes its original IPv4 header plus at least the first 8 bytes of its data, not merely the first 8 bytes of the whole datagram. Current router guidance recommends quoting as much as possible without making the ICMP datagram exceed 576 bytes. See RFC 792, RFC 1812 §4.3.2.3, and RFC 1256.

The lecture's selected table also lists Destination Unreachable codes 6 (network unknown) and 7 (host unknown), plus Source Quench type 4/code 0. Treat these as historical entries, not the normal current examples: RFC 1812 says routers should not generate code 6 and narrows code 7's use; Source Quench is deprecated and must not be used as congestion control (RFC 6633). Code 4, fragmentation needed with DF set, is useful to recognize even though it was omitted from the lecture table.

Obtain initial configuration with DHCP

DHCP lets a joining host lease an address and receive other network parameters. The address can later be renewed or reused after a lease ends or is released. The four messages below describe the initial selection exchange only.

DHCP first lease: Discover, Offer, Request, Acknowledge

Starting state: a host has joined a network and needs an IPv4 configuration. The walkthrough shows the initial lease exchange; no specific offered address or lease duration is assumed.

Discover · find a server

A joining client does not yet have the configured address it is trying to obtain, so it broadcasts DHCPDISCOVER on its local subnet. This begins server discovery. A relay agent can carry the request to a server elsewhere.

Offer · propose configuration

A server returns DHCPOFFER with a proposed address and configuration parameters, including lease information. More than one server may offer; the client has not committed to an offer yet.

Request · select an offer

The client broadcasts DHCPREQUEST to identify the offer/server it selects and request that configuration. In the initial selection exchange, this lets other offering servers know their offers were not selected.

Acknowledge · confirm the lease

The selected server sends DHCPACK with the committed address and configuration parameters. The client can configure itself using the acknowledged values. Lease renewal and rebinding are later states with different addressing behavior, not repetitions of this initial four-message broadcast sequence.

Independent check

Read the message names in order: DISCOVER → OFFER → REQUEST → ACK. The client initiates discovery, chooses an offer, and receives the server's confirmation. DHCP can supply more than an IP address; lease expiry/release makes address reuse possible.

The selected server may be reached through a DHCP relay; it need not share the client's Ethernet segment. Renewal and rebinding use different message behavior from initial DORA. See RFC 2131 §4.1.

Translate an endpoint with NAT/PAT

The lecture motivates NAT by the limited IPv4 address supply. In its example, inside devices use 10.0.0.1 through 10.0.0.3; the router's inside interface is 10.0.0.4, and its public address is 138.76.29.7. The source's 10.0.0/24 label is shorthand; the canonical prefix is 10.0.0.0/24. For TCP/UDP traffic, Network Address and Port Translation (NAPT, commonly called PAT) rewrites the private source address and port to a public address and port, then uses a table to reverse the mapping for replies.

NAT/PAT: follow the request and matching reply

Exact lecture values: inside host 10.0.0.1; public NAT address 138.76.29.7; server 128.119.40.186:80; inside source port 3345; translated port 5001.

Translation table row: WAN 138.76.29.7:5001 ↔ LAN 10.0.0.1:3345.

Inside host sends the original packet

Host 10.0.0.1 sends to server 128.119.40.186:80. The packet is 10.0.0.1:3345 → 128.119.40.186:80. The source endpoint is private; the destination is the server.

NAT creates a mapping and forwards

The NAT router replaces the source endpoint with its public endpoint 138.76.29.7:5001 and records the mapping 138.76.29.7:5001 ↔ 10.0.0.1:3345. The forwarded packet is 138.76.29.7:5001 → 128.119.40.186:80. The destination stays 128.119.40.186:80.

Server reply arrives at the public mapping

The server replies to the endpoint it observed: 128.119.40.186:80 → 138.76.29.7:5001. The public address and translated port identify the NAT mapping that should receive this return packet.

NAT restores the inside destination

The NAT router looks up 138.76.29.7:5001 in its translation table, replaces the packet's destination with 10.0.0.1:3345, and forwards it inside. The resulting packet is 128.119.40.186:80 → 10.0.0.1:3345. The peer source remains the server.

Verify both directions and the checksums

The outbound source 10.0.0.1:3345 became public source 138.76.29.7:5001; the inbound destination was translated back to the original inside endpoint. Address changes require the IPv4 header checksum to be adjusted; TCP/UDP checksums are adjusted when present because their pseudo-header includes IP addresses and the translated port is covered (the IPv4 UDP zero-checksum case remains zero). The map row is the inverse pair used by these four packets.

The lecture's red annotation abbreviates the peer as 128.119.40, 80; the packet labels show the complete server endpoint 128.119.40.186:80, which is used consistently above. A translation requires checksum adjustments: IPv4 header checksum, and TCP/UDP checksum when present because its pseudo-header includes IP addresses. The IPv4 UDP zero-checksum case remains zero. The table is state that enables return delivery, not a record of every network relationship.

NAT can conserve public IPv4 addresses and lets internal addresses change without informing each external peer. Its effect on unsolicited inbound reachability is not a security guarantee: NAT alone is not a firewall or security policy, and explicit mappings can allow inbound traffic. The slide's “security plus?” is an open question, not a conclusion. Its “60,000 simultaneous connections” is a rough lecture estimate based on a 16-bit port field, not guaranteed capacity: usable mappings depend on port allocation, protocol, tuple uniqueness, timeouts and device resources. See RFC 3022 for NAPT bindings and translation/checksum behavior.

NAT also lets an organization change ISP without renumbering its internal devices. The lecture presents a tradeoff: a router that rewrites transport ports goes beyond simple Layer 3 forwarding, and translation weakens end-to-end address transparency. Applications that expect directly reachable peers, such as P2P applications, must account for NAT. IPv6 provides the address-space alternative to sharing scarce public IPv4 addresses this way. The lecture describes NAT as widely used despite these design objections; that is its deployment context, rather than a claim that translation is always the right design.

Common mistakes

  • Sending a remote datagram to the remote host's MAC. Resolve and use the local router's outgoing-interface MAC instead.
  • Saying an IP datagram never changes. Ordinary routers preserve its endpoint IPs, but decrement TTL and update the header checksum; fragmentation or NAT can alter more.
  • Saying the IPv4 checksum protects the whole packet. It checks only the IPv4 header and detects errors; it does not authenticate the header or prevent deliberate alteration. TCP/UDP checksums cover their own data and a pseudo-header; they are not cryptographic security guarantees.
  • Treating ARP as a routed protocol. Its broadcast resolution operates on the local link; it does not cross a router.
  • Mixing ARP cache entries with a switch's MAC-to-port table.
  • Calling the DHCP first-lease DORA sequence the pattern for renewal and rebinding.
  • Treating hidden private addresses behind NAT as proof of security or treating 60,000 as a universal connection limit.

Exam focus

  • Read the header by purpose: version/IHL/length; identification/flags/offset; TTL/protocol/checksum; source/destination; optional options; data.
  • IHL counts 32-bit words; minimum header 20 bytes. Total Length includes both header and data.
  • On a direct link, frame to the destination's MAC. For a remote network, frame to the selected gateway's MAC while retaining the final destination IP.
  • For ARP, resolve the next hop on the local link.
  • Distinguish ICMP type from code; recognize echo, unreachable, TTL exceeded, parameter problem, and the historical Router Advertisement/Solicitation pair.
  • DHCP initial exchange: Discover → Offer → Request → ACK.
  • NAT table row: WAN 138.76.29.7:5001 ↔ LAN 10.0.0.1:3345; replies reverse the destination mapping.

Practice

A host sends to a destination outside its local network. Which MAC address does it need for the first frame?

Check your answer

The MAC address of the selected next-hop router interface on the local link. The IP destination remains the remote host.

What does IPv4 IHL count, and what is the minimum IPv4 header size?

Check your answer

IHL counts 32-bit words. The minimum IHL is 5, so the minimum header is 5 × 4 = 20 bytes.

In NAT state 2, what changes and what stays the same?

Check your answer

The source changes from 10.0.0.1:3345 to 138.76.29.7:5001. The destination stays 128.119.40.186:80; the NAT records the inverse mapping for the reply.

Why is ARP not sent for the remote destination E in the routed example?

Check your answer

A sends the first frame to its directly reachable next hop, router 223.1.1.4. ARP resolves the gateway MAC on A's link; router 223.1.1.4 handles resolution on E's attached link.
