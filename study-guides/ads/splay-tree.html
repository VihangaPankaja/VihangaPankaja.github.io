Splay tree

After access, rotate the relevant node to the root. Frequently used regions tend to stay easy to reach.

Rule and fresh build

Keep ordinary BST ordering. There is no height or color invariant. A single operation can cost O(n), while search, insert, delete and split cost O(logn) amortized over a sequence.

Fresh build from [10, 20, 30]

Input list[10, 20, 30]

1 · Insert 10

With no root or comparison to make, insert 10 as the unique root; its left and right links are empty, so BST order holds and insertion ends.

2 · Insert 20 as a BST leaf

Compare 20 with root 10 and attach it as the right leaf. The new node is the splay node; it has a parent, so continue with one zig.

3 · Zig: left-rotate 10

The right-child zig left-rotates 10 and promotes 20 to root. The middle subtree is empty here; parent/root links and inorder [10,20] are correct, so stop.

Left rotation at 10

Promote right child. Transfer middle subtree the promoted child’s inner subtree to the right of 10, then reconnect the old parent or root pointer. The next state must retain the same inorder key sequence.

4 · Insert 30 and splay

Insert 30 as the right leaf of 20, then splay it by a left zig. The resulting chain can still have linear height; amortized bounds do not promise a balanced shape after each operation.

Splay node and rotation names

Operation Which node is splayed?
Successful search Found node
Failed search or failed delete Last internal node visited
Insert new key New node
Insert duplicate Existing node, whose value is updated
Course bottom-up delete Parent of the physically removed node
split(k) Existing k, or a temporarily inserted k

Zig moves a child of the root up once. Zig-zig handles LL/RR: rotate the grandparent, then the parent. Zig-zag handles LR/RL: rotate the parent, then the grandparent. Repeat until the splay node reaches the root.

Search 10 in the built chain: zig-zig

1 · Locate 10

Search follows 30→20→10 and finds equality, so q=10. Since q is two levels below the root in an LL pattern, perform the first grandparent rotation and continue.

2 · Right-rotate grandparent 30

Right-rotate grandparent 30, promoting 20; its former right subtree transfers to 30-left (empty in this trace). q=10 remains below 20, so one two-level move is not finished yet.

3 · Right-rotate parent 20

Right-rotate parent 20, promoting q=10 and reconnecting it as root. The inorder sequence is unchanged and q has no parent, so splaying terminates; rotating q twice directly would use another first state.

Split and the course join convention

1 · split(20) on keys [10,20,30]

The search for 20 finds the root already, so splaying is a no-op. Split now detaches the root's left and right links; it does not recursively rebalance either side.

2 · Return (S,m,B)

Return S=[10], separator m=20, and B=[30]. Every key in S is less than m and every key in B greater; for an absent split key, the temporary inserted pair is removed and m is null.

3 · join(S, m, B)

With the separating pair m supplied, set m.left=S and m.right=B. This direct three-part course join takes O(1); it is not a two-tree join that must first search for an extremal key.

Top-down form, deletion and caveats

Top-down splaying builds temporary small-key and large-key trees while descending. For LL/RR moves, rotate before linking to the appropriate accumulator. At the stopping node, attach its left remainder to the small tree and its right remainder to the large tree, then make them its left and right subtrees. The target finishes at the root without a separate upward pass.

Course deletion is BST deletion followed by splaying the physical deletion's parent. A common alternative first splays the target, removes the root, splays max(left), then attaches the right tree. This is a different valid algorithm. A two-tree join without a supplied separator also needs that extremal search/splay, O(logn) amortized, O(n) actual. It is not the O(1) three-part join above.

Build from n inserts has O(nlogn) sequence cost from empty. General overlapping meld differs from an ordered join. An empty search has no node to splay. A failed search can still change shape. Keep middle subtrees attached during every rotation.

Is a splay tree guaranteed to have logarithmic height after each operation?

Check your answer

No. The bound applies to operation sequences. A particular tree can be a linear chain.

Bottom-up rotation rules

The tree keeps only the ordinary BST ordering invariant; splaying changes shape but does not impose a height or color bound. A zig is one rotation when q's parent is the root. At greater depth, a zig-zig moves q two levels by rotating the grandparent first and then the parent; a zig-zag rotates the parent first and then the grandparent. In each rotation reconnect the promoted node to the old parent or root, transfer the promoted node's inner subtree, and preserve inorder order. The source diagrams use abstract subtrees; the key-labeled states below make the transferred ranges explicit.

The increasing ten-key construction shows that insertion splays each new maximum to the root using a zig, yet leaves a long left chain. This is a useful actual-cost counterexample: one operation may traverse Θ(n), while search, insert, delete, and split have O(logn) amortized cost over a sequence. Do not read that amortized bound as a per-operation height guarantee.

For deletion edge cases, an empty tree or missing key cannot identify a successful node; on a failed delete, the lecture's missing-search rule splays the last internal node if one exists. Deleting a leaf physically removes that node and splays its former parent; deleting the only root leaves an empty tree and has no parent to splay. A one-child target is replaced by its child, then the removed node's physical parent is splayed (if non-null). For a two-child target, successor/predecessor replacement is only a reduction to physical deletion; the splay target is the parent at that physical removal site, not automatically the logical target or replacement.

Method decision table

Method Decision Stop and edge cases Cost
search(k) Ordinary BST descent; splay found node, otherwise the last internal node visited. Equality stops successfully; empty tree has no q; missing search may change shape. O(n) actual, O(logn) amortized over a sequence
insert(pair) BST insert then splay the new node; for duplicate key update the existing pair then splay that existing node. Empty tree installs root; duplicate does not add a second key. O(n) actual, O(logn) amortized
delete(k) BST deletion then splay the parent of the physically removed node; absent key follows failed-search behavior. Root-only deletion leaves empty tree; root with one child promotes it and has no parent to splay; two-child deletion first finds successor/predecessor. O(n) actual, O(logn) amortized
split(k) Insert k if absent, splay k, detach root's left and right subtrees. If inserted temporarily, discard it and return m=null; otherwise return m=k. O(n) actual, O(logn) amortized
join(S,m,B) Course three-part join with supplied separating pair: attach S and B as m's children. Requires every S key < m < every B key; empty S or B is allowed. No extremal search is needed. O(1) actual and amortized
Top-down search/update Lecture variant partitions into S/B while descending; rotate before linking for LL/RR, then wraps up. Stop at equality or last node before a missing link; restore all accumulator boundary subtrees during assembly. O(n) actual, O(logn) amortized for supported operations
Build by repeated inserts Insert each pair with the course insertion rule, splaying after every new or duplicate pair. Empty input stays empty; define duplicate update policy. A sorted sequence may create a long chain. O(n2) worst actual for a sequence; O(nlogn) amortized
Two-tree join without supplied m Supplemental: find/splay an extremal key, then attach the other tree. This is a different operation from course join(S,m,B). Requires disjoint key ranges; empty operands need explicit handling. O(n) actual, O(logn) amortized
General overlapping meld Not specified as a splay-tree operation in Lecture 11; do not infer it from split/join. Requires a duplicate policy and a separately defined algorithm. Not claimed by the lecture

The lecture states O(1) join for its supplied-separator convention. A different API that accepts only two trees and discovers a separator has additional search/splay work; keep those signatures and costs distinct. The known “splay max(left), then attach right” root-deletion method is a common supplemental variant, not the course's physical-parent deletion algorithm.

Common mistakes and exam focus

  • Name zig-zig/zig-zag from q's two links to grandparent and use the course rotation order; do not substitute two direct rotations of q.
  • Move the promoted node's inner subtree to the demoted node and reconnect the promoted node to the old parent or root.
  • Search miss splays the last internal node; empty search has no node to splay. Duplicate insertion updates and splays the existing pair.
  • Course deletion splays the parent of the physically removed node after successor/predecessor reduction.
  • Split returns S,m,B; if m was temporarily inserted, remove it and return null. Course join assumes m is supplied.
  • O(logn) is amortized sequence cost; actual single-operation cost and worst-case height can be linear.
  • A top-down accumulator trace is not interchangeable with a bottom-up sequence of rotations.
