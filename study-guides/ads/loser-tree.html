Loser tree

Each match stores the loser. The overall winner is kept separately, ready to replay against remembered opponents.

RuleOperations and replayApplications and caveatsBuild an eight-player loser treeTies and exhausted runsReplacement selection: frozen records belong to the next runMethod decision tableTournament applications: identify the correct leaf update

Rule

The loser at the root is the final opponent, not the overall winner. This arrangement makes winner replacement efficient because the old winner's opponents are already stored on its path. Compare the winner-tree sorting walkthrough, then use external sorting to follow merging and replacement selection with the same tournament idea.

Fresh build from players [4, 3, 1, 5]

Input list[4, 3, 1, 5]

1 · Start with four players

Assign fixed identities P1=4, P2=3, P3=1, and P4=5 to the four leaves. No match has been played yet, so internal loser slots are empty and there is no champion; begin bottom-up only after all players are present.

2 · Play the bottom matches

Play the two disjoint lower matches: P1(4) vs P2(3) stores loser P1(4), while P3(1) vs P4(5) stores loser P4(5). The winners P2(3) and P3(1) advance without being stored in those match nodes; continue because they still need a final match.

3 · Store the final loser

Compare the advancing P2(3) and P3(1). Store the final loser P2(3) at the root and keep winner P3(1) outside the tree as the champion. Stop after this match: every internal slot records its own match loser, and the separate champion is the minimum of all four players.

Operations and replay

Initialize in O(n), get winner in O(1), replace winner and replay in O(logn). General key search is O(n). General insert/delete/meld is outside the fixed-player interface. To remove a run from merging, deactivate its player.

Replace winner 1 by 6

1 · Replacement candidate is P3 = 6

P3 is the champion, so replace only its fixed leaf value 1 with 6. The old path opponents are P4=5 at the lower match and P2=3 at the final match; off-path slots still summarize unchanged matches. Start replay at P3’s lowest match and carry the current candidate upward.

2 · First remembered opponent

Compare candidate P3=6 with stored opponent P4=5. P4 wins, so overwrite this match slot with loser P3=6 and carry P4=5 upward. Continue because the old final match depended on P3’s previous subtree winner.

3 · Final remembered opponent

Compare carried P4=5 with root opponent P2=3. P2 wins, so store loser P4=5 at the root and publish P2=3 as the new external champion. Stop at the root: all matches on the changed path are current, and no other subtree changed.

Applications and caveats

Use the tree for k-way merging or replacement selection. In replacement selection, freeze a newly read record when it is smaller than the last output. Frozen records belong to the next run and must lose to every active record, regardless of numeric value. When all records are frozen, end the run and unfreeze them.

For arbitrary nonwinner changes, a winner tree is simpler. The loser-only replay described here assumes the changed player was the overall winner.

Build an eight-player loser tree

This larger supplemental construction uses eight named players and distinct keys so each stored loser can be checked against its exact match. In each diagram, M1–M7 contain the loser, while the overall winner is printed separately below the diagram. Leaves stay in player order; internal slots are never winner summaries.

Build a min loser tree from eight players

1 · Place players in fixed leaf order

The leaves are P1=17, P2=8, P3=12, P4=25, P5=4, P6=19, P7=10, and P8=15. There are seven pairwise matches to play. No internal node has a winner stored in it; each will retain only the loser of its own match.

2 · Play the four bottom matches

M4: P1(17) vs P2(8) → store loser P1(17), carry P2(8). M5: P3(12) vs P4(25) → store P4(25), carry P3(12). M6: P5(4) vs P6(19) → store P6(19), carry P5(4). M7: P7(10) vs P8(15) → store P8(15), carry P7(10). The four winners now enter two matches, so continue.

3 · Play the two middle matches

M2 compares the winners P2(8) and P3(12): store loser P3(12), carry P2(8). M3 compares P5(4) and P7(10): store loser P7(10), carry P5(4). M4–M7 remain valid because their leaf pairs did not change. Continue with the two subtree winners.

4 · Play the final match

M1 compares P2(8) with P5(4), stores loser P2(8), and publishes champion P5(4) outside the match tree. Stop after all seven matches. Check each slot against its own children: M4=P1, M5=P4, M6=P6, M7=P8, M2=P3, M3=P7, M1=P2; the external champion P5 is the minimum of all eight keys.

The heap-order match slots are M1 (root), M2–M3, then M4–M7. This layout makes the path for player P5 explicit: P5 → M6 → M3 → M1. Replaying a changed champion compares it with the loser already stored at each node on that path.

Replace the winner and replay all three opponents

1 · Replace champion P5=4 with P5=20

P5 was the external champion. Replace its leaf with 20 and retain the old path opponents in order: M6 has P6=19, M3 has P7=10, and M1 has P2=8. Start at M6; do not replay unrelated M4, M5, or M7.

2 · Compare at M6

Compare candidate P5(20) with M6’s old loser P6(19). P6 wins, so M6 now stores loser P5(20); carry P6(19) to M3. Continue because M3 still contains the old subtree loser P7 and its prior winner P5.

3 · Compare at M3

Compare P6(19) with M3’s stored P7(10). P7 wins, so M3 stores P6(19); carry P7(10) to M1. Continue because the final match summary has not yet been recomputed.

4 · Compare at M1 and stop

Compare P7(10) with M1’s stored P2(8). P2 wins, so M1 stores loser P7(10) and the separate champion becomes P2(8). Stop at the root. All three replay comparisons are accounted for, and no other match slot changed.

Ties and exhausted runs

The course slide explicitly gives the left-player tie breaker for winner trees (Lecture 1, slide 47). Carry the same deterministic rule into this example: on equal keys the left child advances, and its right opponent is stored as loser. Player identity must travel with a key because equal records can come from different runs.

Tie handling and one exhausted player

1 · Tie on the final match

Starting from the built tree, replace champion P5=4 by P5=8. At M6, P5(8) beats P6(19), so store P6 and carry P5. At M3, P5(8) beats P7(10), so store P7 and carry P5. At M1, P2(8) ties P5(8); left-side P2 wins, so store P5 at the root and make P2 the champion. Stop at M1. The tie changes neither the comparison count nor the need to retain P2/P5 identity.

2 · Mark P5 exhausted and replay M6

When the champion’s run is exhausted, mark its leaf explicitly inactive. At M6, the inactive status loses to live P6(19), so P5 is stored as loser. Carry P6 upward; an exhausted leaf must never be emitted as a data record.

3 · Restore M3 and M1; report no winner only when all are inactive

At M3, compare carried P6(19) with stored P7(10): P7 wins, so store P6 and carry P7. At M1, compare P7(10) with P2(8): P2 wins, so store P7 and publish P2(8). Stop at the root. Repeat this leaf replacement and path replay for every exhausted run; when all leaves are inactive, return “no active player” rather than outputting a sentinel.

Replacement selection: frozen records belong to the next run

This is a supplemental, explicit run-generation trace based on the lecture’s replacement-selection application. A frozen record remains in its player slot but is ranked after every active record, regardless of numeric key. For each emitted item, refill that same run slot if input remains, compare the new key with the last output, and mark it frozen when it is smaller. At a run boundary, end the current run and thaw the held records for the next run.

Freeze a newly read record and begin the next run

1 · Initial active players and first output

Bottom comparison 1: R1(5) vs R2(9) stores loser R2 and carries R1. Bottom comparison 2: R3(12) vs R4(20) stores loser R4 and carries R3. Final comparison: R1(5) vs R3(12) stores loser R3; output R1=5. Suppose R1’s next input is 3. Since 3<5, mark it frozen for the next run and replace R1’s leaf.

2 · Replay the frozen R1=3 against R2=9

Replay comparison 1: retain R1’s numeric key 3 but mark it frozen, so it is ineligible for this run. Active R2=9 advances and frozen R1 is stored as loser. Continue to the final match because the left-subtree winner changed from R1 to R2.

3 · Finish replay and emit R2=9

Replay comparison 2 (right subtree): R3(12) vs R4(20) keeps loser R4 and winner R3. Replay comparison 3 (root): carried R2(9) vs R3(12) stores loser R3 and makes R2 champion. Output 9. If R2 next receives 14, it remains active because 14≥9; replace R2 and replay its exact path, comparing 14 normally against the frozen R1 status (which cannot win this run) and then against the right-subtree champion.

4 · End current run when only frozen records remain

When the tournament has no active player, stop the current run and write its end marker. Thaw the held records only for the next run, then rebuild or replay their tournament state according to the implementation. The numeric minimum among frozen records does not override this boundary.

Method decision table

Method or operation Decision Stop condition Edge cases and course boundary
Build fixed min loser tree Play all bottom matches, then higher matches; store each match loser at its node and carry its winner upward. Keep final champion separately. Finish after n−1 matches; the current page states O(n) initialization. Equal keys use a deterministic left-player rule; preserve player identity. Non-power-of-two padding details are not specified in the lecture.
Read the current winner Return the separate champion, not the root’s stored loser. O(1), with no descent. The root contains the final opponent. If all players are inactive, report no live winner.
Replace current winner and replay Replace that champion’s leaf, compare it against each stored opponent on its leaf-to-root path, write the loser back, and carry the winner upward. Stop at the root; balanced complete tree replay is O(logn), more precisely Θ(logn) in Lecture 1, slide 62. Compare every path opponent. Ties require consistent identity-aware ordering. This procedure assumes the changed player is the current winner.
Replace a nonwinner The page’s stated loser-only shortcut does not cover this safely; use a full rebuild or a separately specified update algorithm. No course loser-tree procedure or bound is given for a nonwinner replacement. A changed nonwinner may affect its local match but the stored losers do not directly expose all subsequent opponents; do not reuse the champion replay claim.
Search for an arbitrary key Scan the player records; match nodes summarize losers, not a searchable key index. Stop at the matching record or after n players; O(n). Key equality alone does not identify the source run.
Insert, delete, or meld players Not part of the fixed-player interface described here; no algorithm or complexity is supplied. No course stop rule/bound. Deactivate a run when its stream ends; that does not imply general dynamic deletion or meld. A changing player count may require a rebuilt layout.
Deactivate an exhausted run Set its leaf to an explicit inactive state, then replay the affected path. Stop at the root; stop the merge when every player is inactive. Inactive loses by state, not by a numeric sentinel. Never emit the status as a record.
k-way merge Keep one current record per sorted run as tournament players; emit the champion, advance only its run, and replay that player’s path. Buffer refill proceeds independently for the run whose input buffer empties. Stop a merge segment when output buffer fills or an end-of-run key is emitted; the complete merge ends when all runs are exhausted. Lecture 2, slides 55–57, specifies per-run queues, a free-buffer pool, double output buffers, async refill, and end marker; do not confuse a buffer boundary with exhaustion of the whole run. Tournament processing for N records is O(Nlogk) (Lecture 2, slide 24); I/O cost is separate.
Replacement selection After emitting the current champion, read that run’s next record. Keep it active when key ≥ last output; otherwise freeze it for the next run. End the current run when no active player remains, then thaw records for the next run. Frozen status sorts after all active records regardless of numeric key. The lecture names run generation as an application; this walkthrough makes the standard status rule explicit.

Complexity claims concern tournament comparisons. They do not include external I/O latency, asynchronous buffer scheduling, or arbitrary dynamic player-set changes. The course’s O(logn) replacement claim applies to replaying the current winner’s path, not every operation that modifies a player.

Tournament applications: identify the correct leaf update

The external-sorting walkthrough traces a winner tree for merging sorted runs and replacement selection. The same choices work with loser storage: keep the champion separately, then replay it against the losers stored along its path. A match node therefore means different data in the two layouts: a winner tree stores the subtree champion; a loser tree stores the match loser/opponent.

Application What each leaf represents After outputting the champion When it ends
Tournament sort of a fresh list One fixed input record Mark that exact leaf inactive; replay its ancestors. Do not refill it. Every original record has been output.
k-way merge The current head of one already-sorted run Advance only the winning run and install its next head; make that leaf inactive at run EOF. Every input run is exhausted.
Replacement selection One in-memory candidate slot Read the next input record into the slot. Keep it active if it is at least the last output; otherwise freeze it for the next run. No active candidate remains; close the run, thaw frozen records, and begin the next run.

All three choose a minimum from eligible leaves, but only k-way merge advances an existing sorted stream, and only replacement selection classifies new records into the current or next run. A plain tournament sort never turns its remaining records into longer initial runs. Its output is one sorted ordering of the fixed input; run-length improvement is the distinct replacement-selection algorithm. The tree comparison work is O(logk) per changed champion, while disk reads and writes depend on buffers and runs. The winner-tree walkthrough shows the fixed-leaf sort and counts comparisons; the run-based examples are in external sorting.
