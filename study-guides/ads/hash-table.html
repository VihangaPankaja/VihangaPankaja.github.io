Dictionaries and search trees / Lecture 8

Hash table

Compute a bucket from the key. Fast exact lookup is the strength; sorted order is not maintained.

Big picture and ruleOperationsStatic hashing and caveatsWhat the lecture guarantees

Big picture and rule

A dictionary stores key/value pairs. An ordinary dictionary has unique keys, so inserting an existing key updates its value. A multimap explicitly allows duplicate keys. Collision handling must preserve every record that hashes to the same bucket.

Fresh build from keys [12, 7, 17], using h(k)=k mod 5

Input list[12, 7, 17]

1 · Allocate five empty buckets

Five slots are allocated before any key is stored. The modulo rule maps each key to exactly one bucket; no comparisons or collision handling occur until an insertion lands in an occupied slot.

2 · Insert 12

Compute 12 mod 5 = 2 and place key 12 in bucket 2. That bucket was empty, so the new chain has one node and lookup for 12 stops after this first comparison.

3 · Insert 7 and 17

Both 7 mod 5 and 17 mod 5 equal 2. Append them to bucket 2, preserving all three distinct dictionary keys; a lookup continues through the chain until equality or its end.

Operations

Operation Procedure Expected / worst case
get(key) Hash, then inspect that bucket O(1) / O(n)
put(key,value) Update a match or add a new pair O(1) / O(n)
remove(key) Find pair, then unlink or mark its slot O(1) / O(n)
build Insert n pairs O(n) expected, O(n2) worst without collision guarantees
meld Rehash the donor's pairs into the result Linear expected in processed pairs
range / rank / nearest match Scan or additionally sort No native ordered-tree guarantee

Expected O(1) assumes a suitable hash function and controlled load. Rehashing a whole table takes linear time. If collision buckets use balanced trees, bucket operations can have logarithmic worst-case bounds, under that implementation's assumptions.

Search 17, delete 7, then update 12

1 · Search 17

Hash 17 to bucket 2 and compare the chain in order: 12 differs, 7 differs, and 17 matches. Stop at equality; reaching the chain end instead would prove the key absent.

2 · Delete 7

Find 7 after comparing 12, then unlink only the interior node. The 12-to-17 link is reconnected, preserving reachability; deleting the head would instead move the bucket head to its next node.

3 · Put key 12 again

Hash 12 to bucket 2 and find an equal key at the head. Replace its value in place rather than adding a second record, so unique-key dictionary size remains two; a multimap would use a different duplicate policy.

Static hashing and caveats

Perfect hashing has no collisions among a fixed known key set. Minimal perfect hashing uses exactly n target slots. The lecture names CHD, Compress, Hash and Displace, with linear construction and constant search in its stated model. A query outside that set still needs a membership check.

Supplemental implementation detail: open addressing uses probing instead of chains. Deletion needs a tombstone or a correct cluster repair, because an empty slot can prematurely stop searches. The step viewer uses chaining throughout.

Why is a hash table a poor direct fit for best-fit bin packing?

Check your answer

Best fit needs the smallest remaining capacity ≥ the item size, an ordered lower-bound query. Exact hashing does not locate that successor directly.

What the lecture guarantees

Lecture 8 presents dictionaries as key-element pairs and distinguishes unique-key dictionaries from dictionaries that permit duplicate keys. The dynamic dictionary operations are get(key), put(key, element), and remove(key). Its hash-table comparison gives expected O(1) and worst-case O(n) for these operations; balanced search trees used for overflow can give O(logn) under that overflow strategy. The lecture also warns that hashing does not directly support nearest-match, range, or rank/index queries. The collision-chain and resizing demonstrations below are explicitly supplemental implementation examples.

get(key) / search Compute the bucket, then compare keys in that bucket; stop on equality or when its chain/slot proves there is no match. Empty bucket or missing key stops with “absent.” Expected O(1), worst O(n) in the lecture's hash-table model.
put(key, element) Search the target bucket first. For this unique-key dictionary, replace the matching element; otherwise insert a new pair. Existing key updates without increasing record count. A dictionary-with-duplicates/multimap may retain multiple values, as lecture 8 slide 4 illustrates. Expected O(1), worst O(n).
remove(key) Find the matching pair and unlink it from its collision representation. Handle head, interior, tail, sole-node, empty-bucket, and missing-key cases. Expected O(1), worst O(n).
Supplemental open-addressed search/update/delete Probe according to the table's sequence, stopping at equality or a slot that proves absence; update on equality, insert at an available slot. Deletion generally needs a tombstone or correct cluster repair so later keys remain searchable. Not the chaining method used by the viewers.

meld(A,B) Supplemental: insert or rehash each donor pair into the result using the result's own capacity and hash function. Expected O(n+m) processed pairs under hashing assumptions; worst O((n+m)2) for naive repeated insertion into one chain. Lecture 8 does not specify a hash-table meld algorithm.
nearest match / lower bound No direct hash-table decision: hashing chooses a bucket by equality hash, not key order. Scan all records or maintain a separate ordered index; neither gains a hash-table ordered-query guarantee.
range query No direct bucket-local stopping rule can exclude all keys outside a numeric interval. Scan all n records, or use a separate ordered structure. Hashing is not suitable for range queries in lecture 8.
ascend() Hash buckets do not maintain global key order; collect and sort records if ordered traversal is required. Lecture 8 gives O(D+nlogn), where D is bucket count.
get(index) / remove(index) No ordered rank is encoded by a bucket address; the lecture's hash-table route sorts/organizes records to answer index operations. Lecture 8 gives O(D+nlogn); this is not the O(1) exact-key operation.
Best-fit successor query (lecture application) Find the smallest available capacity ≥ item size, reduce that capacity, then update the pair or start a new bin if none qualifies. Hashing is a poor direct fit because this is a nearest-match query; lecture 8 proposes a dynamic dictionary with duplicates and then a balanced BST for O(nlogn) total processing.

Ten keys, one collision chain

This fresh construction uses ten distinct keys, all congruent to 2 modulo 5. Each insertion is shown, so the final chain is not inferred only from its endpoint. This deliberately creates the worst collision pattern for separate chaining; it is a teaching input, not a claim that modulo hashing usually behaves this way.

A successful search for 57 compares ten keys, while a missing key hashing to 2 also compares ten. Reversing chain insertion order changes which successful key is found first but cannot remove the worst case.

Search, update and contrasting deletion positions

The existing three-key example demonstrates a successful tail search, interior deletion, and update. The following supplemental states contrast head/interior/tail unlinking and missing-key termination with a compact bucket-array view. The bucket head is a pointer to the first chain node; removing the head changes that pointer, while an interior removal reconnects predecessor to successor.

Supplemental resize and hash assumptions

The lecture does not prescribe a load-factor threshold or a resizing rule. To make those assumptions visible, this example uses a supplemental policy: start with 5 buckets, grow to 11 when the next insertion would make n / capacity > 1, and recompute every bucket using h(k)=k mod capacity. A resize is not moving a chain wholesale: every existing key must be rehashed because its bucket number can change.

Rehashing costs O(n) work to move n records, plus allocation proportional to the new bucket count. Expected O(1) lookup requires a suitable hash distribution and controlled load; worst-case chain length can still be n even after resizing. The concrete modulo-11 example distributes this particular key set but is not a universal hash guarantee. If chaining overflows into balanced search trees, lookup within a bucket may be O(logn) as the lecture notes; that bound depends on the chosen per-bucket tree and its maintenance.

Perfect hashing: keep the claim narrow

Lecture 8 names perfect hashing (no collisions), minimal perfect hashing (exactly n slots), CHD, O(n) construction, and O(1) search for the fixed set. It cites “Compress, hash, and displace” by Botelho, Belazzougui, and Dietzfelbinger (ESA 2009). The lecture does not provide the CHD construction steps or a dynamic update algorithm, so this page does not invent either. Static perfect hashing is appropriate when the key set is fixed. For an arbitrary query key, verify the key stored at the candidate slot; otherwise a non-member could be mistaken for a member.

Common mistakes

  • A collision does not mean two keys are equal. Retain every distinct pair in the chosen bucket.
  • In a unique-key dictionary, check for a matching key before adding; update its element rather than creating a duplicate record.
  • Deleting a chain head changes the bucket's head pointer. Deleting an interior node changes its predecessor link. A missing key changes nothing.
  • Resize by rehashing keys under the new capacity/hash function. Copying old bucket positions can make lookups search the wrong place.
  • Expected O(1) depends on hash distribution and load assumptions. The lecture's worst-case O(n) remains possible.
  • Exact lookup is not nearest-match, range, or rank lookup. Those operations need an ordered structure or a full scan.
  • A perfect hash is collision-free only for its fixed known key set; verify candidate membership for arbitrary queries.

Exam focus

  • Lecture dynamic dictionary: get(key), put(key, element), remove(key).
  • Hash table: expected O(1), worst O(n) per primary operation; balanced-tree overflow is O(logn) under that bucket strategy.
  • Perfect hashing: no collisions for the fixed set; minimal perfect uses n slots; lecture states CHD construction O(n), search O(1).
  • Collision handling must preserve all key-element pairs. Unique-key put updates; duplicate-permitting dictionaries may retain multiple entries.
  • Resizing changes the mapping: recompute each key's bucket. A low load factor helps expected performance but is not by itself a worst-case guarantee.
  • Hash tables do not directly maintain sorted order, ranges, nearest matches, or rank/index positions.

Practice

With h(k)=k mod 5, where does 37 go? It goes to bucket 2 because 37 mod 5 = 2. If bucket 2 already contains 12, 17, and 22, append or prepend 37 according to the chosen chain policy, while preserving all four keys.

In the ten-key chain, how many key comparisons can a missing key 62 require? Ten: it maps to bucket 2, where all ten stored keys must be checked before the chain end proves absence.

Why can a resizing implementation not just leave key 12 in old bucket 2 after growing to 11? Because 12 mod 11 = 1; lookup computes bucket 1 and would miss it if the record stayed in bucket 2.

What does minimal perfect hashing guarantee according to lecture 8? For its fixed n-key set, it uses n slots with no collisions; the lecture states O(n) construction and O(1) search. It does not describe dynamic insertions.
