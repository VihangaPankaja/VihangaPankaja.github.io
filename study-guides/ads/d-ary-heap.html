d-ary heap

Give each parent more children to shorten the tree. Removal then compares more children at each level.

Rule and representation

A d-ary min heap is complete and obeys min-heap order. With 1-based indexes, parent(i)=⌈i−1d⌉, for i > 1. Children run from d(i−1)+2 through min(di+1, n).

Build from a list

Copy the list and heapify from the last parent toward the root for O(n) with fixed d. The viewer shows the alternative fresh build by insertion.

Build from a fresh list [7, 3, 9, 1, 5]

Input list[7, 3, 9, 1, 5]

Start empty

The empty array has no root or parent relation to check, so the repeated-insertion build starts with zero records and stops until the first append.

Append 7

Append at the next complete-tree slot. Now compare upward.

Appending 7 puts it at 1-based index 1, the only complete-tree slot. A root has no parent, so sift-up stops and min-heap order is vacuously true.

Insertion of 7 complete

The item has reached the root or an ordered parent. Heap order is restored.

The root remains 7 and still has no children. No comparison can violate order; this insertion is complete at the root.

Append 3

Append at the next complete-tree slot. Now compare upward.

Appending 3 at index 2 preserves breadth-first completeness. Its parent is ceil((2−1)/4)=1 with key 7, so shape holds but order requires an upward swap.

Bubble 3 above 7

Swap with the parent. Continue only if the next parent is larger.

Compare child 3 with parent 7 and swap because 3<7. It reaches index 1, where no parent exists; stop with 3 no larger than every child.

Insertion of 3 complete

The item has reached the root or an ordered parent. Heap order is restored.

The item is now the root and there is no next parent comparison. Sift-up stops; equality with a parent would also be a valid stopping condition.

Append 9

Append at the next complete-tree slot. Now compare upward.

Appending 9 at index 3 completes the next breadth-first slot. Parent index ceil((3−1)/4)=1 has key 3, so the new edge is already ordered.

Insertion of 9 complete

The item has reached the root or an ordered parent. Heap order is restored.

Since 9≥3, stop at its first parent comparison. Existing edges were valid and appending created no other new edge.

Append 1

Append at the next complete-tree slot. Now compare upward.

Appending 1 at index 4 preserves completeness. Its parent is still index 1 with key 3, and 1<3 requires another upward repair.

Bubble 1 above 3

Swap with the parent. Continue only if the next parent is larger.

Swap 1 above parent 3. The new location is the root, so there is no further parent; stop with all children at least 1.

Insertion of 1 complete

The item has reached the root or an ordered parent. Heap order is restored.

After the swap 1 is root and all remaining keys are no smaller. The insertion stops; a parent equal to 1 would also stop without swapping.

Append 5

Append at the next complete-tree slot. Now compare upward.

Appending 5 at index 5 fills the root’s fourth and final child position. The parent index is ceil((5−1)/4)=1, key 1, so no repair is needed.

Insertion of 5 complete

The item has reached the root or an ordered parent. Heap order is restored.

Since 5≥1, stop at the root parent. The 4-ary shape and every parent-child ordering are valid.

Remove minimum from a 4-ary heap

1 · Start

The root has four children.

The starting 1-based array is [1,7,9,3,5]; the root has exactly four children at indexes 2–5. Save minimum 1, remove last key 5, and move it to the root of the 4-item heap.

2 · Replace 1 with last value 5

The children are 7, 9 and 3. The last parent has fewer than four children.

With active size 4 the root has only indexes 2–4 as children: keys 7, 9, and 3. Compare all existing children, choose 3, and note the missing fourth child at index 5; replacement 5>3 so continue downward.

3 · Swap with the smallest child

The replacement is now a leaf. Stop.

Swap 5 with the smallest existing child 3, giving [3,7,9,5]. The replacement is now at index 4, whose first child index is 14>n=4, so it is a leaf and sift-down stops.

Cache behavior and caveats

The lecture's cache example puts four 8-byte nodes in a 32-byte line. A shifted, aligned 4-heap keeps siblings together, reducing cache misses during removal. This is a layout-specific advantage, not a universal speed guarantee. Increasing d indefinitely makes child selection expensive. For fixed d = 4, height is about half a binary heap's height.

Does a shallower heap always do fewer comparisons?

Check your answer

No. A d-ary removal examines up to d children at each level. Fewer levels can trade against more comparisons per level.

Scope and index formulas

This page uses a 4-ary min heap for every worked state: a complete breadth-first array, with each parent no greater than any existing child. Lecture 3 numbers the root 1 and gives the general d-ary formulas. For fixed d=4, a node at position i>1 has parent ceil((i−1)/4); its possible children occupy positions 4(i−1)+2 through min(4i+1,n). For example, position 12 has parent 3, and position 3 has children 10–12 when n=12. Check the upper bound before reading children: the final parent can have one, two, or three children.

The lecture describes the complete-tree representation, height, 4-ary removal tradeoff, and cache-layout observations. Search, located deletion, key updates, and meld below are standard single-ended heap methods added to make the method choices explicit; they are not separate procedures specified on the d-ary lecture slides. “Located” means a valid handle or maintained key-to-index map is already available.

Method decisions

Method Decision Stop condition Edge cases and cost
build(list) by bottom-up heapify Copy records in breadth-first order; sift each parent from ceil((n−1)/4) down through 1, always selecting the smallest existing child. At a leaf, or when the parent is no greater than the smallest child. Empty/singleton arrays require no comparisons. For fixed d=4 the standard bottom-up build is O(n); lecture 3 names the process of examining bottom-up for the interval heap, while this array min-heap use is the standard d-ary extension.
build(list) by repeated insert Append each record at the next complete slot; compare upward with its single parent. Root reached or parent key ≤ inserted key. Equality stops. Worst case O(nlog4n); the five-key viewer shows this alternative, not bottom-up heapify.
getMin / peek Read the root without mutation. Return immediately. Empty heap has no minimum; otherwise O(1).
insert Append at position n+1 and swap upward while the new key is strictly smaller than its parent. Root reached or parent ≤ key. Equal keys need not swap. Worst case O(log4n) levels and parent comparisons.
decreaseKey(handle) Lower the located key, then compare only with successive parents and swap upward as needed. Root reached or parent ≤ updated key. It must not increase the key. O(1) to locate by handle plus O(log4n) repair; key search itself is not included.
removeMin Save root, move the last key to the root, shrink n, then select the smallest among up to four existing children and swap downward if it is smaller. No children, or replacement ≤ smallest existing child. Empty fails; singleton becomes empty. One to three children are compared when present. Worst-case O(4log4n) child comparisons, plus bounded moves.
increaseKey(handle) Raise the located key, then sift downward by the smallest existing child. Leaf reached or updated key ≤ smallest child. It must not lower the key. O(log4n) repair after location is known. This is the standard single-ended extension paired with the page’s remove-min row.
search(key) Scan the array; a min-heap array is not sorted, so no logarithmic binary search applies. Match found, or all n positions checked. Duplicates may return any match unless identity is requested. Worst-case O(n).
delete(handle) Save the target record, replace its slot with the final array record, and shrink. If replacement < parent sift up; otherwise sift down. Up: root or parent ≤ replacement. Down: leaf or replacement ≤ every existing child. Deleting the last record needs no repair; deleting root is removeMin. Maintain the handle/index map through swaps. O(log4n) repair after location is known; find-by-key remains O(n).
meld(A,B) Supplemental array implementation: concatenate records and bottom-up heapify with fixed d=4. Each parent sift reaches a leaf or an ordered child set. O(n+m) for fixed d, including array copy. Handles must be remapped if identity is retained. No meld algorithm is specified on lecture 3’s d-ary slides.

These are worst-case bounds unless marked otherwise. A 4-ary heap has height Θ(log4n), about half the levels of a binary heap, but remove-min selects among up to four children per level. The lecture reports about 1.6 upward levels on average for uniformly distributed inserts, versus the worst-case height bound; it does not claim a universal reduction in comparisons. Its cache example depends on node size and alignment: with four 8-byte nodes per 32-byte line, shifting the 4-heap by two array slots places siblings in the same line, for about log₄ n L1 misses per average removal versus about log₂ n for the standard mapping. The lecture reports roughly 1.5–1.8 heapsort speedup for one million keys under its stated comparison; neither result guarantees a gain for every workload.

Bottom-up heapify: twelve keys, fixed d=4

Use the list [18, 7, 22, 3, 14, 9, 30, 5, 11, 2, 17, 8]. With n=12, the last parent is ceil((12−1)/4)=3, so process positions 3, 2, then 1. Every changed array state appears below. Stop if the parent equals its minimum child. Tied minimum children can be resolved consistently; they do not prevent a required swap with a larger parent.

Bottom-up 4-ary heapify of [18, 7, 22, 3, 14, 9, 30, 5, 11, 2, 17, 8]

Input list[18, 7, 22, 3, 14, 9, 30, 5, 11, 2, 17, 8]

1 · Copy all twelve records

2 · Process position 3

3 · Process position 2

4 · Root compares four children

5 · Root repair continues one level

The final array is [2, 5, 8, 3, 14, 9, 30, 7, 11, 22, 17, 18]. The root’s children are 5, 8, 3, 14, each at least 2. Position 2 has children 9, 30, 7, 11; position 3 has children 22, 17, 18. Both parents are no greater than their own children. A sift-down follows one parent–child path; it never swaps directly between separate subtrees. The construction preserves all twelve records and the complete shape.

Remove minimum: four children, then a partial child set

This second heap is a valid 12-record 4-ary min heap chosen to expose both selection cases: [1, 5, 4, 6, 7, 12, 13, 14, 15, 8, 9, 11]. The root has four children; position 3 has three children before removal. Removing the final record shortens that child set to two.

Remove 1 from [1, 5, 4, 6, 7, 12, 13, 14, 15, 8, 9, 11]

Input list[1, 5, 4, 6, 7, 12, 13, 14, 15, 8, 9, 11]

1 · Save the minimum

2 · Move last record to root

3 · Compare only the two remaining children

4 · Swap 11 with 8 and stop at the leaf

The result [4, 5, 8, 6, 7, 12, 13, 14, 15, 11, 9] retains all records except the removed 1. Root 4 is no greater than 5, 8, 6, and 7; position 3’s partial child set 11 and 9 is no smaller than 8. If the replacement had equaled the selected child, repair would stop because equality satisfies heap order.

Located key changes: repair follows the changed edge

Start with the heapified twelve-key array above. A handle identifies the record even if another record has the same key; update its stored index after each swap. Decreasing a key can violate only its parent edge; increasing it can violate only its child edges.

Decrease and increase a located key

1 · Start before decreasing key 30

2 · Change 30 to 1 at the same position

3 · Swap to position 2

4 · Reach the root

5 · Reset, then increase key 5 at position 2 to 16

6 · Stop at a leaf

The two repairs keep the same multiset except for the explicitly changed key. Do not scan for a key and call that operation O(log4n): a key-only search is O(n); the logarithmic bound starts after a valid handle or index is known.

Common mistakes

  • The root is numbered 1 in the course formulas. Do not plug a zero-based array position directly into ceil((i−1)/4).
  • ceil((i−1)/4) is the parent position for 1-based i>1; index 1 has no parent.
  • The child interval is clipped by n. Compare only existing children, including one-, two-, and three-child final parent cases.
  • During remove-min, select the minimum child first, then compare the replacement with it. Choosing another child can leave a smaller key below the replacement.
  • Equality satisfies heap order. Do not swap equal parent/child keys just to keep moving.
  • A heap is not a sorted array. General key search remains linear, and duplicate keys require a handle if a particular record must be changed or removed.
  • Fewer levels do not guarantee fewer comparisons: a 4-ary remove scans up to four children per level. Cache benefits in the lecture rely on the stated aligned layout and node size.

Exam focus

  • Complete tree, breadth-first 1-based numbering; parent ceil((i−1)/d) and children d(i−1)+2 ... min(di+1,n).
  • Fixed d=4 gives height Θ(log4n), approximately half the binary heap’s levels. Worst-case insertion follows one parent per level; remove-min examines up to four child keys per level.
  • Insert/decrease: append or update, then move upward while child < parent; stop at root or parent ≤ key.
  • Remove-min/increase: move last or updated key downward using the smallest existing child; stop at leaf or when key ≤ that child.
  • Bottom-up list heapify starts at the last parent and proceeds toward the root; repeated insertion is a separate build method.
  • Handle-based update/delete costs assume the record’s location is already known. Search by key is O(n).
  • Lecture cache claim: four 8-byte nodes fit a 32-byte line; the stated 4-heap shifts by two slots so siblings share that line. Treat it as a layout-specific observation.

Practice questions

For d=4, n=12, and i=3, which child positions exist?

Answer

Positions 10 through min(13,12)=12: three children, not four.

During remove-min, the replacement is 9 and its existing children are 6 and 6. Must it swap?

Answer

Yes. The smallest child is 6, and 9>6. Either tied child may be selected; after the swap continue from the selected child’s position.

Does a handle make searching by arbitrary key O(log4n)?

Answer

No. The handle supplies the location; finding a matching key without one still requires a linear scan in the general case.
