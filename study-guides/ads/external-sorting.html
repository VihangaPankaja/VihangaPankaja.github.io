External sorting

Make sorted runs that fit in memory, then merge them. Count disk transfers before counting comparisons.

Big picture

An external sort handles data too large for RAM. A run is a sorted sequence on disk. Run generation creates the first runs; merge passes combine them until only one remains. The winner-tree page shows how to repeatedly select a champion, and the loser-tree page shows the alternative that stores each opponent. These tournament layouts support both run generation and k-way merging, but the leaf update rules differ. Sequential transfers are much cheaper than repeatedly seeking between distant records.

Build runs from a fresh list

With memory for M records, the simple method reads M records, sorts them internally, writes one run and repeats. It produces ceil(N/M) runs. The final chunk can be shorter. Sorting stability depends on the internal sort and the merge tie rule.

Replacement selection: longer initial runs

Keep k candidates in a min tournament or heap. Output the smallest eligible candidate, then replace it with the next input. If the replacement is smaller than the last output, freeze it for the next run. Frozen players remain in their fixed slots but cannot win this run, even if their numeric key is small. When no active candidate remains, close the run, thaw the frozen players and start again. EOF makes a slot explicitly inactive. The walkthrough below keeps all three states visible: active, frozen for the next run, and inactive because no input remains.

Fresh replacement selection: k=3, input [4,1,7,2,0,6,3,8]

Input list[4,1,7,2,0,6,3,8]

1 · Load the first candidates

2 · Output 1; read 2

3 · Output 2; read 0

4 · Output 4; read 6

5 · Output 6; read 3

6 · Output 7; read 8, then output 8

7 · Unfreeze and drain

The work is O(Nlogk) comparisons. Except for a final partial run, a run has at least k records. Sorted input can form one run; reverse-sorted input produces runs of about k records. Under the usual random-input model, expected run length is about 2k; this is not a worst-case guarantee. Use run number, key and player identity to make frozen states and ties explicit. See the loser-tree replay.

Multiway merging and buffers

A k-way merge keeps one current head per nonempty run. A winner/loser tree chooses the next output in O(logk), followed by one replay. Heap selection is another option. Total comparison work is O(Nlogk) per pass. Ordinary buffered merging requires k input buffers and one output buffer. Fan-in is limited by RAM, file handles and buffer sizes.

Three-way merge: buffers and head updates

1 · Assign buffers

2 · Output 1 and replay A

3 · Output 2 and replay B

4 · Continue, flush and refill

Asynchronous buffering. The lecture's overlapping-I/O scheme uses two output buffers and a pool of at least k+1 input buffers; 2k input buffers are sufficient with the stated dynamic allocation. Predict the next input buffer to exhaust using its last key, with a consistent tie rule. Merely fixing two buffers permanently to every run does not express the same allocation strategy.

Pass counts and I/O costs

With B-record blocks, Q=ceil(N/B) blocks and R initial runs, approximately ceil(log_k R) merge passes are needed when R>1. Each full read/write pass transfers about 2Q blocks. Generating batch runs adds another read/write pass; final output pipelining or uneven last blocks can change the exact count.

P=⌈logkR⌉,block transfers≈2Q(1+P)
Work the lecture example: N=10,000, M=500, B=100
  1. RAM holds 500 records, so batch generation makes 10,000/500=20 runs.
  2. Each complete dataset occupies 100 blocks. Run generation reads 100 and writes 100 blocks: 200 transfers. The slide's model charges 20 internal-sort costs as well.
  3. Binary merge: ceil(log₂20)=5 passes. Each full pass costs 200 transfers, plus the model's merge-processing cost. Including generation gives about 1,200 transfers.
  4. Five-way merge needs ceil(log₅20)=2 passes: about 600 transfers including generation if five input buffers plus an output buffer fit.
  5. With only five 100-record buffers, reserve one output buffer: fan-in is at most four. Then ceil(log₄20)=3 merge passes, giving about 800 transfers. Smaller buffers can alter this tradeoff.

The lecture's abstract five-way pass calculation and its memory example must be reconciled before choosing a physical buffer layout. Transfer-time symbols in the slides are model parameters, not measured timings.

Unequal runs: choose a merge schedule

If a record crosses several merges, it is read and written several times. Minimize weighted external path length: merge the smallest runs first, just as in a Huffman tree. For lengths [4,3,6,9], merge 3+4=7, then 6+7=13, then 9+13=22. Weighted merge volume is 7+13+22=42 record units; read plus write contributes twice that volume. An equal-depth schedule costs 44 units here. For k-way trees, add zero-length dummy runs until the leaf count is congruent to 1 modulo k−1; do not write dummy data.

External quicksort and double-ended queues

External quicksort partitions around a sorted middle set in RAM. A double-ended priority queue exposes both its minimum and maximum. Small and large output buffers collect records on the corresponding side; input buffers feed the partition. When the middle fills, a new extreme can be sent to its side, or a middle extreme can be expelled to make space for an intermediate item. The actual algorithm also maintains partition boundaries and buffer positions.

One partition decision at a time (supplemental small example)

1 · Build a middle set from [4,6,8]

2 · Read 2

3 · Read 10

4 · Read 5; choose to expel minimum

5 · Finish the partition

The interval heap, dual heaps and correspondence heaps support the middle set. Expected quicksort behavior needs partition assumptions; bad partitions can cause quadratic work. The merge-sort I/O formula above does not apply to external quicksort.

Common mistakes and exam focus

Do not confuse memory capacity, block size and merge fan-in. More fan-in reduces passes only when buffers fit. A frozen key is deferred, not deleted. Stable sorting needs a defined tie rule through both run generation and merging. Run exhaustion is an inactive state, not an ordinary key that happens to be large.

There are 17 runs and room for four input buffers plus one output buffer. How many merge passes?

Check your answer

Fan-in k=4. The run counts are 17 → 5 → 2 → 1, so three passes.

Walkthrough: merge sorted runs one winner head at a time

Each input run is already sorted. The tournament only compares the current head from each live run. After emitting a champion, replace that head from the same run; do not advance every run, and do not copy the old winner into another leaf. Build costs k−1 comparisons. Each of N outputs changes one leaf and replays at most the tree height, so merging uses O(Nlogk) comparisons and O(k) tree storage. In the worked six-record merge the exact count is 7 key comparisons (2 to build, then 2+2+1+0+0+0 for the six winner updates); there are six output records and six head advances/exhaustions. These are CPU comparison counts. Disk-buffer reads and writes are a separate cost. The diagram uses explicit inactive leaves for padding and EOF, never a fabricated key. For globally stable output across arbitrary runs, include original sequence position in the comparison key.

Walkthrough: replacement selection with exact run boundaries

Replacement selection also keeps a tournament over a fixed number of RAM slots, but it refills the winning slot from the unsorted input. If the incoming key is at least the last output, it remains eligible for this run. If it is smaller, freeze it for the next run. A frozen record is retained, but active records beat it regardless of numeric value. When no active record remains, flush the current run’s end marker, thaw the held records, and continue as a new run. This is the source of longer initial runs; plain tournament sort does not do this.

For N input records and k candidate slots, tournament comparisons are O(Nlogk), with O(k) in-memory candidate space; every record is read once and written once into exactly one initial run. This worked input creates runs of lengths 6 and 3 from k=4 slots, using 10 key comparisons (3 to build, 4 during run 1 replacements, 2 to rebuild after thawing, and 1 during run 2). The lecture states sorted input can make one run, reverse order yields about N/k runs, and expected run length is about 2k under its random-input model; those are replacement-selection observations, not a guarantee for every input and not a claim about plain tournament sort. I/O overlap and block-buffer allocation affect elapsed time separately from tournament comparisons.

Does a fresh-list tournament sort use replacement selection’s freeze rule?

Check your answer

No. Tournament sort repeatedly emits the minimum and makes that fixed leaf inactive. Replacement selection reads a new record into the emitted slot, keeps it active if it is at least the last output, and freezes it otherwise. Only replacement selection can defer a smaller arrival to a later initial run.
