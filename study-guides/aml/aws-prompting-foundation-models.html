Big picture

A prompt is the input contract for a foundation model: it describes the task, supplies relevant context, and shapes the response. Prompting can guide a pre-trained model without changing its parameters. When the task or data demands more control, the choices expand to retrieval-augmented generation (RAG), fine-tuning, or continued pretraining. These approaches solve different problems and carry different data, quality, latency, cost, and operational tradeoffs.

This is an optional AWS course companion. It is separate from the assumed CS4681 examination route. The service names below describe the course's 2025-era comparison and are not current availability, price, or suitability recommendations.

Build a prompt from the task outward

A useful prompt gives the model enough direction to produce a response that can be evaluated. Its parts are building blocks rather than a required fixed order.

Prompt components and the question each component answers
ComponentPurposeExample cue
TaskWhat should the model do?“Compare the short-term and long-term impacts.”
Instructions / stepsWhat process or boundaries should it follow?Classify, summarize each side, then conclude.
Context / input dataWhat situation or material should ground the response?A balanced overview of plant-based diets.
ExamplesWhat input/output demonstrations clarify the expected task?A representative sample with the desired kind of response.
RoleWhat perspective should shape the answer?An energetic food educator.
AudienceWho should be able to use the answer?Teenagers.
Tone / styleHow should the response sound?High-energy and educational.
Output formatWhat structure makes the result usable?Title, then Introduction, Body, Conclusion.
ConstraintsWhat should be included or avoided?Do not discuss weight; do not reveal the audience.

The course recommends clear, specific directions, useful context, an explicit outcome, and examples when they clarify expectations. Organizing a prompt so context comes before the task can make the request easier to interpret; it is a practical pattern to test, not a universal guarantee. XML-like tags can mark sections so their purpose is recognizable. Tags organize text; they do not create capabilities or enforce security boundaries.

Plant-based diets: a tagged prompt

The following preserves the course's tagged prompt structure and its content constraints. Its role and audience guide the voice, while the final task tells the model what response to produce.

<tone>
You are a high-energy TV chef who is passionate about food education. Your audience is teenagers.
</tone>

<context>
We are discussing plant-based diets and want to give a balanced view.
</context>

<instructions>
Classify the short-term and long-term impacts of plant-based diets. Summarize each group and finish with a concise conclusion.
</instructions>

<constraints>
Do not discuss weight. Do not reveal that the audience is teenagers.
</constraints>

<response_format>
Start with a title. Then use these labeled sections, each with its section name and a colon:
Introduction:
Body:
Conclusion:
</response_format>

<task>
Using the role, context, instructions, constraints, and response format above, write the response.
</task>

The reusable pattern replaces a concrete context, audience, topic, or requirement with a named placeholder, then fills those fields for a new task. After a first response, refine one prompt element at a time, compare against the same criteria, and keep the change only if it improves the desired outcome. A structured output is useful only when the requested labels and content are checked in the actual response.

<tone>{role, energy, and style}</tone>
<context>{situation, topic, and background}</context>
<instructions>{steps the model should follow}</instructions>
<constraints>{required inclusions and exclusions}</constraints>
<response_format>{requested structure and labels}</response_format>
<task>{specific deliverable using the sections above}</task>
Worked refinement: tighten an underspecified diet prompt

Given: the starting request is “Tell me about plant-based diets.” The desired response should be balanced, distinguish short-term from long-term impacts, avoid weight, speak in an energetic food-educator voice to teenagers without naming the audience, and use a title plus three labeled sections.

  1. Check the starting prompt against the requirements. It states the topic only. It does not define the reader, balance criterion, time horizons, exclusion, role/tone, or output structure.
  2. Assign each missing requirement to a component. Put the audience and desired voice in the tone/role section; the balanced topic in context; the classify/summarize/conclude sequence in instructions; the two exclusions in constraints; and the title plus Introduction, Body, Conclusion labels in response format.
  3. Place the deliverable in a final task. Ask the model to write the response using those named sections. Keep context before the task so the task can refer to the supplied situation.
  4. Review the prompt specification before evaluating an output. Confirm that each requested requirement appears once, the constraints do not contradict the requested structure, and the expected sections are concrete enough to check.

Static prompt check: all six requirements above are represented in the tagged example. This checks the prompt design itself; it does not claim a model response has been generated or measured.

Condition the input, refine the output

Zero-shot, single-shot, and few-shot prompting differ by the number of examples included in the input: none, one, or several. These examples condition inference; they do not update model parameters. Choose examples that represent the requested task and vary the count experimentally when the result is inconsistent.

Reasoning-oriented prompt labels in the course can be translated into observable request strategies:

  • Chain of thought (CoT): ask for a task broken into explicit, checkable steps, such as listing assumptions before a calculation.
  • Tree of thought (ToT): ask for a small set of candidate approaches, compare each against stated criteria, and select one.

These are output and decomposition strategies. A generated explanation is not evidence of faithful access to hidden internal reasoning, and either strategy can still produce errors. Check intermediate claims or final results against the task.

Output refinement can happen in several places. A prompt can be revised and rerun; an ensemble can combine multiple candidate outputs; reranking can score candidates and select one; post-editing can normalize a response; filtering can remove responses that fail a rule. These add work and do not by themselves establish correctness. High-impact decisions need a defined evaluation method and appropriate human review.

If an application offers tools such as search or an external action, a prompt can request their use only when the application has actually integrated them. Naming a tool in text does not invoke a system, grant access, or authorize an action. The application must enforce permissions and validate arguments and results outside the model.

Choose and evaluate a foundation model

Model selection begins with the task and the acceptance criteria. A model that is capable in general may still be a poor fit for a particular language, modality, context length, latency budget, or data policy.

Consider task-specific capability; required modalities and languages; context-window needs; customization options; model size relative to task complexity; throughput and latency; hardware and integration requirements; operational effort; scale; price and licensing; and privacy, data rights, ethics, and regulatory constraints. Pre-trained model training data may not be fully visible to the user, so data quality, coverage, recency, and bias can be difficult to establish from the model description alone.

For example, a healthcare question-answering use case has a higher consequence of unsupported or misleading output than a low-stakes internal drafting assistant. That changes the required evaluation, oversight, controls, and acceptable cost. A cheaper or faster result is not a successful selection if it misses the task's quality or safety bar.

Evaluation should use representative examples and metrics tied to the actual job. Compare candidate models with a consistent test set, inspect failures, refine the approach, and document why the selected model meets the criteria. Metrics are evidence about defined behavior, not a general truth certificate.

In production, keep monitoring behavior and user feedback, revisit the evaluation set as tasks or data change, and reassess after model or system changes. A multi-model design may assign different subtasks to different models, but coordination and end-to-end evaluation still matter.

Inference controls shape generation

Inference controls affect how a model generates from its current input. They do not teach it new parameters. Temperature changes the sharpness of a next-token distribution: lower positive values make high-logit choices more dominant; higher values spread probability more broadly. Top-k keeps a fixed number of highest-probability candidates. Top-p keeps a probability-ranked prefix until its cumulative mass reaches a threshold, so the number retained can vary. Maximum generation length limits output size, while a stop sequence ends generation when the specified sequence appears.

The worked calculation below uses a deliberately hypothetical single-context logit vector. It demonstrates the arithmetic, not an AWS model's probabilities. The softmax equation is defined here for positive temperature. A literal T = 0, API ranges, control interactions, and processing order are model-specific; no universal combined-control order is implied. Sampling controls do not ensure a true or safe answer.

Adaptation choices change different things

Start with a prompt when clearer instructions, examples, or context may be enough. Add retrieval when the task needs relevant external or frequently changing material at inference. Fine-tuning or continued pretraining changes model parameters and requires a suitable training path and data. These are different mechanisms, with different setup and review costs.

In RAG, an application retrieves passages relevant to a query and adds them to the model input. The model uses those passages during inference; retrieval does not update model weights. Retrieval quality, indexing coverage, permissions, and freshness affect the context the model receives. More retrieval also adds latency and may add irrelevant or conflicting material. RAG can support grounding and citations when the system supplies and checks them, but it does not guarantee accuracy, security, or privacy.

What changes, what data path is involved, and when the approach may fit
ApproachWhat changesData pathTypical reason to consider it
Prompting / input examplesCurrent input only; no parameter update.Instructions, context, and optional demonstrations are supplied at inference.Clarify task behavior or provide a few task examples quickly.
RAGRetrieved context in the inference input; no parameter update.Documents are prepared/indexed; each query retrieves relevant material and augments the prompt.Use changing, domain-specific, or externally maintained knowledge.
Fine-tuningModel parameters are updated from task examples.Curated labeled or input/output examples enter a training process; evaluate the resulting model.Improve consistent task behavior or a target style when prompting alone is insufficient.
Instruction fine-tuningParameters are updated using instruction-following examples.Instruction, input, and desired-output pairs enter training and evaluation.Adapt responses to a family of instructed tasks.
Continued pretrainingParameters are updated by continuing the original pretraining-style objective.A suitable additional corpus enters a training process; assess coverage and risks.Adapt broader language/domain patterns when that training approach is justified.

Training data, retrieval context, and inference prompts must not be conflated. Training changes parameters; RAG selects context at query time; prompting supplies the immediate instruction and input. Each needs appropriate data preparation, evaluation, access controls, and human oversight. Do not claim that any route guarantees accuracy, confidentiality, security, or legal compliance.

Worked adaptation choice: answer questions from weekly policy updates

Given: an assistant answers questions about policy documents that change weekly. The answers should refer to the current policy text. A pre-trained foundation model is available; the team has no labeled task examples and does not need to teach a new writing style.

  1. Compare the problem with prompting. Clear instructions can tell the model to answer from supplied policy context, but a prompt alone does not provide the changing documents. Manually pasting a large policy set into every request is not a dependable freshness plan.
  2. Compare the problem with parameter updates. Fine-tuning or instruction fine-tuning requires curated examples and changes model parameters. It does not automatically insert the newest weekly policy. Continued pretraining is a broader corpus adaptation, not a query-time document lookup.
  3. Choose a retrieval path for the stated need. Prepare an authorized, versioned document index; for each question, retrieve relevant passages and add them beside the question in the inference prompt. Refresh the index as the authoritative policy changes. This is RAG; the model weights remain unchanged.
  4. Check the whole path before relying on answers. Use representative questions with known policy references. Check that the retrieved passages are relevant, current, and permission-appropriate; inspect whether the answer is supported by those passages; then assess latency, cost, and cases requiring human review. A retrieval result or citation is evidence to inspect, not a guarantee.

Decision: RAG directly addresses the changing-knowledge requirement. If the requirement instead became consistent behavior across many examples, evaluate instruction fine-tuning as a separate option with suitable training data and model evaluation.

Prompt attacks and defensive thinking

The course introduces adverse prompt categories as risks to recognize and test conceptually. Do not treat a prompt as an access-control system: instructions alone cannot grant or revoke an application's real capabilities.

Adverse prompt categories at the course's conceptual level
CategoryConceptual riskDefensive question
Prompt injectionUntrusted input attempts to change or override the task instructions.Are trusted instructions separated from user or retrieved content, and are outputs checked?
Prompt leakingA request attempts to expose hidden instructions or training-related information.Does the system avoid placing secrets in model-visible prompts and limit data access?
JailbreakA request attempts to bypass intended restrictions.Are capabilities bounded and behavior tested against representative adversarial cases?
Social engineeringAn appeal to authority, urgency, or helpfulness tries to elicit a restricted action.Do authorization checks happen outside the model and apply to every sensitive action?

The course's scenarios include account-transfer or sensitive account requests, requests for protected training information, harmful-software assistance, and attempts to obtain security-protocol details. Treat them as defensive evaluation prompts only; this guide does not reproduce or execute attack text. Consider secure prompt construction, least-privilege integrations, authentication and authorization outside the model, input/output validation, capability limits, adversarial testing, monitoring, and human escalation. These controls reduce risk but are not guarantees. A course-era service control such as Bedrock Guardrails is an example of a control surface, not a complete security boundary.

Common mistakes

  • Treating a role label, negative instruction, or XML-like tag as a hard access-control rule.
  • Calling zero-shot, single-shot, or few-shot prompting “training”; examples in the prompt do not update weights.
  • Confusing RAG's inference-time retrieval with fine-tuning or continued pretraining, which update parameters.
  • Reading top-p as a percentage of vocabulary size instead of cumulative probability mass.
  • Assuming temperature or a high likelihood makes an answer factual, safe, or appropriate.
  • Comparing models with a metric that does not measure the task, or treating similarity to a reference as proof of truth.
  • Treating course-era service descriptions and example parameter settings as current universal API recommendations.

Course review

This companion is outside the assumed CS4681 exam scope. For course review, be able to identify prompt components and explain how iteration changes a result; distinguish input conditioning, inference-time retrieval, and parameter updates; choose evaluation evidence that matches a task; explain the qualitative role of generation controls; and compare approaches by quality needs, data path, control, latency, cost, and operational effort.

Practice questions

Recall: A prompt asks for a balanced comparison, specifies teen readers, forbids discussing weight, and requires three labeled sections. Name the four prompt components represented.

Check your answer

Task/instructions: produce a balanced comparison. Audience/context: teen readers and the plant-based-diet topic. Constraint: do not discuss weight. Response format: the three labeled sections. A role or tone can be added separately.

Recall: A team adds two worked examples to a prompt. Did it fine-tune the model? Why?

Check your answer

No. The examples condition the current inference input. Fine-tuning uses training data to update model parameters.

Apply: A knowledge assistant needs current policy documents that change weekly. Which approach directly supplies the selected policy passages at query time, and what must still be evaluated?

Check your answer

RAG can retrieve and add passages to the inference context without changing model weights. Evaluate retrieval relevance, coverage, freshness, access permissions, conflicts, latency, and whether generated claims are supported by the retrieved text. Retrieval does not guarantee a correct answer.

Apply: From the worked T = 1 baseline, top-p = 0.9 retains A, B, and C. What is the retained mass and why is D excluded?

Check your answer

The cumulative masses are A = 0.643914, A+B = 0.880797, and A+B+C = 0.967941. The third prefix is the first to reach 0.9, so it is retained. D would extend the prefix after the threshold was already reached.

Recall: A translation benchmark reports a higher BLEU score for one candidate. What can that support, and what does it not establish by itself?

Check your answer

Under a consistent benchmark and reference setup, it supports stronger n-gram overlap with the reference. It does not by itself prove faithful meaning, fluency, task suitability, or truth; inspect outputs and use task-appropriate human evaluation too.

Apply: A retrieved passage contains an instruction telling the model to ignore the user's request. Name the risk category and one system-level defense.

Check your answer

This is a prompt-injection risk from untrusted retrieved content. Keep trusted instructions structurally separate, treat retrieved text as data, constrain tool capabilities with external authorization, validate outputs, and test the behavior. Prompt wording alone is not a security guarantee.

Apply: A team needs consistent output style across many related tasks after prompt iteration is insufficient. Which adaptation might it evaluate, and what changes in that approach?

Check your answer

It might evaluate fine-tuning, including instruction fine-tuning when instruction-following examples fit the task. Training examples update model parameters; that differs from adding examples to an inference prompt. The team must curate training data and evaluate the adapted model and its operational risks.
